# Grade canonical architecture runs

Grade the anonymous run against its request, pinned source, installed skill, and canonical evidence.
Do not infer which candidate produced it.
Read the named source before deciding architectural truth.
Treat earlier reports as retained evidence rather than fresh canonical authoring.

## Per-feature verdicts

Return one verdict for every declared feature.
Use `pass`, `missing`, `incorrect`, or `not-applicable` from the result schema.
Presence alone does not establish correctness.
Cite source files, stable canonical subjects, commands, or captures.
A waiver needs a concrete reason from the request.

## Findings

Each result below pass carries a finding with `did`, `taught`, `passage`, and `gap`.
Use `conformance` for a departure from the installed skill or explicit request.
Use `truth` when the run follows the skill but contradicts the source.
Use `skill` when the expectation appears nowhere in the installed guidance.
A declared feature that cites the governing passage receives a conformance finding.

## What correct use means

One vault holds one canonical model.
Modules form a containment forest without fixed levels.
Each module owns its outgoing relationships.
Independent collections describe complete behavioral exchanges.
Readings select content without storing another definition.

Continuing subjects keep their identities through edits and renames.
Proposals preserve their exact predecessor and independent state identities.
Comparisons retain separate selected and comparison revisions.
Checkpoints retain exact architecture without selecting current.
An author uses complete revisions, explicit claims, public intents, and configured Git signing.

The author never patches live architecture files directly.
Only explicit requests authorize adoption or migration.
A legacy refusal requires inventory, owner identity choices, preview, and explicit installation.
Names and bindings do not establish shared identity.

Read-only inspection, locality, branch footprint, rendering, and navigation preserve architecture bytes.
Exports retain reproducible canonical recipes.
Local agents and the existing local renderer remain the execution owners.
An explanation preserves its captured subjects, state, checkpoint, and comparison revision.
It authors no architecture.

## What the skill adds unprompted

Use the installed skill catalogue when the source establishes a feature.
Judge the same stable feature keys across retained reports.

## What the run inherited

Compare raw canonical readings and derived semantic evidence before and after the run.
Credit newly supplied or improved requested meaning.
Do not credit a feature that the fixture already supplies.
Preserve unrelated current architecture and active proposals.

## What you can and cannot see

Open every declared capture before a visual verdict.
A missing capture leaves visual evidence incomplete.
Do not infer visual quality from source text or receipt dimensions.
Separate architectural truth from the renderer's placement choices.
Do not infer unseen interaction from a static capture.

## Scores (0-10 each)

Score accuracy, completeness, clarity, and visible readability from observed evidence.
Use the declared result schema.
Explain deductions with concrete source or capture references.
A plausible picture does not excuse incorrect meaning or an unauthorized write.

## Planning runs

If the request plans unimplemented architecture, judge its explicit requirements and internal coherence.
Do not demand source that the request says does not exist.
Distinguish proposed responsibilities from implemented facts.
Keep proposals unadopted unless the request authorizes adoption.

## Concerns

Record fixture, instruction, source, and capture limits that prevent supported verdicts.
Name the affected feature and evidence.
A harness failure does not establish an author failure.
