## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The README images, clips, banner and narrated videos were made by an ad hoc kit that lives in a Claude job scratch directory, with machine paths in its scripts. Nobody can rerun it from the repository. The shell redesign and the renderer changes leave them showing an older product, and every later change to the shell or the renderer will do the same. The README must be refreshed whenever what it shows changes, so the way to refresh it has to live in the repo, be named, and be easy to find. The SVGs come from the renderer. The clips are filmed from the real shell in headless Chromium and encoded with ffmpeg. The banner art is made with Codex image generation. The narrated videos are recorded with the two-pass recorder and need Codex voice. The owner chose that staleness is listed by a command and does not fail `bun run check`.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 `bun run readme:assets <name>` regenerates one README asset from the checkout. With no name it regenerates every asset that needs no Codex sign-in. The assets that need Codex (the banner art and the narrated videos) run only when named or with a flag.
- [x] #2 No script holds a path from one machine. Chromium, ffmpeg and the scratch directory come from the environment or from ARCHBOARD_* variables with a stated default. The kit runs from a fresh clone after `bun install` and `bun run build:frontend`, and leaves nothing in the repository except the assets and the manifest.
- [x] #3 The vault that the clips are filmed over is authored by the kit from tracked inputs, or is a tracked example, and is never copied from a scratch directory.
- [x] #4 A manifest in docs/readme names each asset, the command that makes it and a hash of the sources it shows. `bun run readme:check` lists the stale assets and exits non-zero when any is stale. It is not part of `bun run check`.
- [x] #5 One short document says how the assets are made, which need Codex, and when to refresh them. The archboard-dev skill tells a task that changes what the README shows to run `readme:check` before it closes, and CLAUDE.md points to the document.
- [x] #6 Fast tests cover the staleness logic. No test lane films anything.
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Inventory how each file in docs/readme was made, from README.md, the git log of docs/readme and the old kit. 2. Build scripts/readme-assets on what the repository already has (the headless Chromium module, the rasterizer, the recorder, the Chromium and ffmpeg discovery) and port only the pointer, key and screencast steps the recorder cannot do. 3. Declare each asset in docs/readme/assets.json with its command, its sources and a recorded source hash, and add readme:check to list the stale ones. 4. Document it in docs/agents/readme-assets.md, in the archboard-dev closing steps and in AGENTS.md. 5. Cover the staleness logic with fast repository-lane tests. Dry-run the Codex assets and leave the images alone until the geometry settles. No board is affected: this is tooling around the README.
