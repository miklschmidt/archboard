## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The user wants the voice agent to give a walkthrough as a talk: explain each step aloud, move the pane to the next step when it has finished speaking, and let the person interrupt at any point to ask something before it moves on. The constraint that shapes this is in DESIGN.md: the GPT-Live voice model never sees tool calls or tool results, only coordinator prose prefixed [BACKEND] under a 1,000-token budget. So a step cannot reach the voice model as data; the coordinator has to navigate the pane and then hand the step over as prose. The flow the user described: voice asks the coordinator for the next step; the coordinator drives the pane there through a typed tool and is told when the pane has finished navigating (TASK-250 exposes that); the coordinator then delivers that step to the voice model, which speaks it; the voice model asks for the next step only when it is done, so an interjection simply delays that. Presentation position stays presentation state the browser owns; the coordinator drives it the way it already drives live panes. Open question to measure rather than assume: a coordinator turn per step may be too slow, in which case the whole script could be delivered at the start with only navigation per step.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A person can ask the voice agent to present a walkthrough, and the linked pane enters the presentation at its first step
- [ ] #2 The coordinator moves the pane to a step through a typed tool that answers only once the step has finished arriving, or with the reason it could not
- [ ] #3 After each step has arrived the voice model receives that step to explain, and the next step is requested only after it has finished speaking
- [ ] #4 A person interrupting mid-explanation gets an answer, and the presentation does not advance until the voice agent asks for the next step
- [ ] #5 A step the person changes by hand, or leaving the presentation, is told to the coordinator and voice model so the narration follows the picture
- [ ] #6 Time from the end of one explanation to the start of the next is measured and recorded in the task
- [ ] #7 Covered by coordinator and tool contract tests, and verified end to end with a real voice session
<!-- AC:END -->

1. Shared contract: SemanticPaneContext gains presentation {walkthrough, step, of, arrived} | null (read-only telemetry; the browser still owns the position). New socket message pane_present (enter at step / go to step / leave). PRESENTATION_ARRIVAL_TIMEOUT_MS in src/shared/timing, below the browser command lease.
2. Browser: useWalkthrough accepts a driven place; the stage derives one arrival fact (no camera glide, no picture flight, the step's reading drawn, fitted to the step) and reports it through the pane reading; pane-session handles pane_present and routes it to the pane's stage. DOM arrival attributes stay for the browser owner.
3. Server: a presentation port that sends pane_present to the coordinator's linked pane and resolves when that pane's own report says the step arrived, or refuses with the reason (no pane, no such walkthrough/step, left by the person, timeout, cancelled). A reported position the server did not drive is a person's change.
4. Tool: archboard_voice.present_step {step} (coordinator-only namespace, beside resolve_spoken_approval; archboard_app is workhorse-only). Host supplies pane, board, variant and walkthrough; the model supplies only the step. Result carries position, heading, body, subjects so the coordinator has the manuscript without a second read. Classified like wait_threads: no approval, blocks, cancellable. New manifest digest => retained coordinators are replaced on restart (by design).
5. Voice start in presentation mode: realtimeStart gains presentation {walkthrough}; the server renders a byte-bounded script of that walkthrough into the voice prompt with the loop instructions (ask the orchestrator to present step 1 when ready; narrate what it hands back; ask for the next only when done; answer interjections first), and a presentation section into realtimeStartInstructions for the coordinator (call present_step, then hand the step back as speakable prose under the [BACKEND] budget). UI: a Present control on a chosen walkthrough that enters the presentation at step 1 and starts voice in this mode.
6. AC5: a person's step change or leaving is injected into the coordinator history and appended to the voice session (catalogue-updates discipline: deduplicated, never retried); a step change asks the voice to narrate that step now, leaving is told quietly.
7. AC6: the server measures assistant_finished -> next assistant_started across each present_step and records it per step; numbers from the real session go in this task.
8. Tests: tool contract + dispatcher (validation, replay fingerprint, refusals, cancellation), presentation port (arrival, person change, timeout), start policy/process contract envelope, stage tests for driven place and arrival, browser owner for a server-driven step. Docs: DESIGN.md, ADR 0023 note, codex-workbench-authored-contracts.md, voice acceptance script for the human run (AC7).
