## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
clangd needs `compile_commands.json` to know the include paths and flags of each file. Without it, clangd guesses, and a guess is no better than a candidate.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A C, C++ or Objective-C candidate resolves through clangd when the checkout has `compile_commands.json`
- [ ] #2 Without `compile_commands.json`, the check says so once and reports candidates
<!-- AC:END -->

Decisions:
1. clangd is a default on the PATH (ADR 0046 already says so), because with the check's flags it runs no code of the project: measured, no compiler run without --query-driver, no plugin loaded from -fplugin=, -Xclang -load or -fpass-plugin= (in --check, as a server and while indexing), no file written for -MF, -o, -save-temps, -ftime-trace, --serialize-diagnostics, -fcrash-diagnostics-dir, -fprofile-instr-generate.
2. Background index ON, not off as the brief suggested, in a directory of the server's own. Measured: with it off, the same question named ledger.h's declaration, then ledger.c's definition once ledger.c had been opened, and didClose did not undo it; --index is an obsolete flag. So answers would depend on question order. With --compile-commands-dir=<own> holding a copy of the database, the index went to <own>/.cache/clangd/index; nothing was written in the checkout or ~/.cache/clangd. The client waits for the end of backgroundIndexProgress after its first open (requestMs bounds it; a timeout is language-server-failed once). Index time: Redis 303 commands 1.4-1.6 s, libuv and leveldb ~0.1 s on 24 cores.
3. The copy (not a symlink) makes each command's directory absolute and moves its module cache: clangd wrote the -fmodules-cache-path a command named into the checkout for an @import (measured). Every -fmodules-cache-path, also after -Xclang, is dropped and one in <own>/modules goes before `--`.
4. Readiness: the nearest compile_commands.json clangd would find (the file's directory and each above it to the checkout root, then build/ there), on disk also where Git ignores it, not one whose real path is outside the checkout. Not reused from c-resolution.ts: that finder reads only Git-listed files (CMake's ignored build/ would never count) and is internal to createCResolver; only splitCommand is reused. A database with no command, or invalid, is unready too: clangd then starts no index and reports no progress (measured), so the wait would hang to its bound. Unready is said once per checkout (no database) or per database. compile_flags.txt does not count: clangd builds no index from it.
5. --enable-config=false: a .clangd and ~/.config/clangd/config.yaml are both loaded by default (measured); a .clangd can add flags, load an index file and name a remote index server (network; this nixpkgs build has no remote support, so that part is from clangd's documentation). No flag turns off only the project's file, so the user's config is off too; INSTALL.md says to put flags in compile_commands.json. --clang-tidy=false so no .clang-tidy is read. Never --query-driver. The check's flags come after an entry's args and win (a repeated flag is allowed and the last wins, measured). CLANGD_FLAGS in the server's environment is the user's and is left alone; INSTALL.md says that a --query-driver there runs compilers.
6. No settle request for the parse: a definition request right after didOpen is answered after the parse (Redis db.c answered 80 ms after the open, after the server.h preamble). clangd refuses a question about an unopened file, so opensFiles.
7. languageId: clangd takes the language from the compile command; a .h opened as c, cpp or objective-c gave the same outline and answer (measured), so .h maps to c and no header text is sniffed (the coordinator's note about SyntaxFacts.adapter does not arise: the row never reads it).
8. Objective-C on Linux, -x objective-c -fobjc-runtime=gnustep-2.0, no SDK: superclass method sends, super, an id receiver and [[Ledger alloc] init] each resolved to the @implementation in another .m; a missing <Foundation/Foundation.h> import did not stop the parse.
9. Evidence: a C use whose include leads only to a declaration (TASK-367.09's candidate) is asked whenever a part makes it, not only where the name match joins two parts, because the declaration is usually in the using part's own header pair (Redis server.h), so the match cannot say which part the code is in. Cost on the Redis board: 146 ms -> 3.1 s warm.
10. Language servers now imports Code facts (splitCommand); drawn on the board as Language servers -> Code facts.
11. The stand-in server is run by path from code-check/tests (spawned, never imported), so the code-check owner needs no second stand-in.

The reviewer ran clangd 21.1.8 from nixpkgs clang-tools through the check's own session, on scratch checkouts. strace -f listed each program that clangd started and each file that it opened for writing. The reviewer also read the clang 21.1.8 sources of the driver, of clangd and of the tooling layer.

Findings and fixes:

1. Code of the checkout ran. This is a must-fix. clangd runs clang's driver on every compile command. When a CUDA, HIP or OpenMP command asks for the native GPU, the driver runs a program to find it. These are the only programs that the driver runs before it compiles (getSystemGPUArchs in ToolChains/Cuda.cpp and AMDGPU.cpp). A script of the checkout ran 1 to 6 times for one command, both for an opened file and in the index. The command named the script with --nvptx-arch-tool= or --amdgpu-arch-tool=. Or it put the script where the driver looks: in a -B directory, in a --cuda-path, or beside the compiler that the command names. It also ran for -mcpu=native on amdgcn, for -march=native on nvptx64, and for an OpenMP target with no architecture. A response file, a driver configuration file beside the compiler (clang.cfg), and a file that --config names all worked too. A -sectcreate at the end of a command took the flag that the copy added there as its value. No plugin loaded, as the build measured. Fix b16fd0d44, in compile-database.ts: the copy drops response files, -B, --prefix and --config. It drops every argument that names a module cache or a GPU program, in any spelling (-Xclang=, -Wp, and /clang:). It drops everything from --. It moves a compiler named with a directory into the server's own directory, under the same name. Right after the compiler, it puts its own module cache and a GPU program that does not exist, spelled /clang: for clang-cl. There, no flag of the command can take one of them as its value. After the fix, the same 30 commands ran nothing of the checkout. clangd tried only the missing program in its own directory.

2. CLANGD_FLAGS. This is a must-fix. With CLANGD_FLAGS=--query-driver=**, clangd ran the compiler that a command names (measured). The trust rule of ADR 0046 lets a server run project code only from an entry that the user writes for trusted checkouts. clangd is a default for every registered checkout, so its flags must be the check's. The prepare of a row now also returns the environment, and clangd starts without CLANGD_FLAGS. Flags of the user's go in args of a c entry. This reverses decision 5 for CLANGD_FLAGS.

3. Writes outside the server's own directory. This is a must-fix. -Xclang=-fmodules-cache-path= wrote the module cache into the checkout. A response file that holds -Xclang -fmodules-cache-path= did the same. -Wp, and -Xpreprocessor did not. clangd also wrote preamble-*.pch and the driver's toolchain-program-*.txt into /tmp. When clangd is killed, those files stay there. The fix is the drops above, with TMPDIR and XDG_CACHE_HOME set to the server's own directory.

4. The own directory outlived a stopped server. This is a must-fix. nixpkgs' clangd is a shell script that runs clangd-unwrapped as its child. A kill ended only the script. A kill comes from an index that does not end within the bound, from a failure or from a cancel. clangd-unwrapped then went on with its index. It wrote 158 shards into the directory after the check removed it (measured on Redis with a request bound of 300 ms). Each server now starts in a process group of its own (Bun.spawn with detached). A kill ends the whole group (killGroup in connection.ts). A broken output stream does the same. The removal retries. A spawn can throw, for example after the directory of the project has gone. The own directory is then removed too. Reruns with the real clangd left no directory and no process. The reruns were a normal close, an index past the bound (three runs), an abandoned pass, and a kill of clangd during its index.

5. A test crossed an owner boundary. Fix bb5785d04. clangd-check.test.ts spawned the private stand-in of the language-servers owner by its path. Lint cannot see a spawn, but the owner then depended on the private support of another owner (docs/agents/boundaries.md). code-check/tests/clangd-stand-in.ts now answers definitions and outlines, and reports the progress of the index. Two mutations were run: without the declaration rule of resolution.ts, and without the server site of support.ts. Each made one of its tests fail. The commit body says that each of its four tests fails. That is more than was run.

6. The detail of an unready database named the wrong cause. A database whose link leads outside the checkout read as no database. A database that is not valid JSON read as one that lists no command. Each now says what it is, and an outside link is said once for each database.

7. Docs, in d806decf9. INSTALL.md said that clangd runs no code with those flags, and that CLANGD_FLAGS loses to the flags of the check.
