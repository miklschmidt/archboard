## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The archboard skill currently has seven human-graded prompts but no runnable model evaluation harness or reproducible board fixtures. We need evidence that reducing skill discovery work saves tokens without sacrificing architectural truth or diagram quality.

Agreed scope:
- Use the real open-source Flask repository (https://github.com/pallets/flask), with exact commit pins and historical revisions. Candidate changes include contextvars and JSON-provider changes in Flask 2.2 and Sans-IO base extraction in 3.0; verify selected source revisions when implementing.
- Evaluate an installed skill in an isolated consumer checkout and vault, without archboard developer instructions or source leaking into author context. Verify installation independently.
- Author with gpt-5.6-luna at high reasoning; grade all runs in one independent gpt-6-astra session at high reasoning. Base execution on codex runs.
- Baseline means the pre-overhaul skill package; candidate means the rewritten package. Hold the Archboard CLI, Codex executable/version, fixture revisions, prompts, model settings and supplied context constant. Preserve a reproducible baseline before rewriting.
- Three repetitions per scenario per skill version, run in parallel with independent state. This is an explicit, on-demand model evaluation workflow, not part of the fast default test gate.
- Most prompts identify the architectural question and relevant real source paths. Include one broader codebase-mapping case and report it separately.

Existing owned-canvas test support provides isolation/lifecycle precedent. Codex exec JSONL provides execution events and token usage; inspect the actual chosen CLI contract at implementation time. No model evaluations or implementation were run in this planning session.

Semantic feature grading is an explicit per-eval contract, not only a general quality score. Each scenario declares the expected set of Archboard features and what correct use means for that real Flask use case. Maintain a suite coverage map for applicable features: configured node/relationship kinds and board levels, containment and actual receiver endpoints, traffic modeling, configured grouping under TASK-207, code bindings, drill-down links, flows/message kinds, views, walkthroughs, variant identity/comparison and adoption. Choose features because the scenario calls for them; do not reward adding unrelated features to increase a score.

The blinded Astra judge checks each declared feature against saved semantics, source evidence and the relevant rendered or runtime output. Report pass, missing, incorrect or not-applicable with evidence and a reason; declared required features cannot be silently marked not-applicable. Missing or incorrect expected features fail semantic compliance even when the diagram looks plausible. Presence alone is insufficient: assess whether usage expresses the actual architecture.

Grouping cases must use TASK-207 configured group IDs and explicit multiple memberships across containers, with no inherited membership or legacy singular group field. Relevant inspection cases assess members and internal/boundary relationships. Traffic cases assess meaningful directed flow and supported speed/volume semantics, without presenting illustrative animation as measured telemetry. Static renders alone cannot prove motion; distinguish persisted traffic correctness from any claim about observed animation. Final grouping evaluations require a CLI implementing TASK-207, pinned identically for baseline and candidate.

Schema-audited coverage inventory (2026-09-14; recheck against the implementation revision):
Every feature below needs a named scenario/checklist entry and evidence owner. Expand the seven legacy cases where needed; seven is not a suite-size cap. Several features may share a realistic Flask scenario, but do not force all features onto one board. Scenario families below are coverage assignments to make concrete in the canonical eval definitions.

1. Architecture creation and editing — board name and configured level, initial variant name/summary, empty-board creation followed by population, and board-level level changes; nodes with name, configured kind, responsibility and longer description. Preserve or intentionally clear optional fields on updates.
2. Containment and relationships — optional/nested single parent, truthful parent-child structure, real internal receiver endpoints and whole-module endpoints only where semantically appropriate; directed from/to, configured relationship kind, optional label/description, and every emphasis value (normal/default, hero, muted).
3. Illustrative traffic — omitted/off, enabled with defaults, explicit positive finite speed and volume, changing and removing traffic, and effective-default equivalence in identity/comparison. Judge architectural justification separately from numerical validity and visual motion evidence.
4. Code binding and linked detail — optional/unbound planned nodes; registered repo identity and repo-relative path; optional branch, commit and confirmedAt fields with truthful evidence and preservation semantics; drillDown board plus both current and named variant selectors. A missing named target must not silently become current. Source-level detail boards remain separate from proposals.
5. Ordered sequences — flow name/summary, participant identity and column order, step identity/from/to/label, all message kinds (sync/default, async, return, self), optional note, repeat >=2, and a single-participant self flow. Correct self endpoints, sequencing, insert/delete/reorder and continuing action identity. Use real source-grounded exchanges rather than inventing Flask behavior to satisfy coverage.
6. Shared views — name/summary and both architecture/data-flow grammars; all/default scope and selection of nodes, edges and flows in the combinations allowed by runtime grammar validation. Cover node-region relationships versus explicit-edge isolation, automatically included endpoints/participants/ancestor context, and board-owned view edits across variants. Cover a selected subject removed from one comparison side and a view empty in both sides without falling back to all.
7. Walkthroughs — name/summary, ordered beats with heading/body, references to every allowed subject class (node, edge, flow, step), an introductory beat with no subjects, explicit view switching versus omitted view, and stable beat identity across reword/reorder/add/remove. Cover coherent repair when referenced subjects or shared views change.
8. Efficient authoring inputs — existing IDs and names, missing IDs minted by the product, same-write as handles on supported node/edge/flow/step inputs and their reference consumers; one batched edit, full-definition replacement with field preservation, and each remove collection (nodes, edges, flows, views, walkthroughs). Removing nested steps/beats is expressed through the enclosing definition. Ensure untouched subjects remain untouched.
9. Variants and adoption — initial current, branching from current and a named predecessor, competing branches/descendants, proposal summary, draft/current/historical lifecycle, current designation versus lasting identity, and adoption with optional reason/history. Judge added/removed/changed/unchanged subjects against the direct predecessor, including continuing versus replacement edges and sequence subjects; consistent shared-view comparison.
10. Family reconciliation — noncompeting inheritance and agreement, all reported disagreement kinds (competing-field, competing-order, deleted-and-changed, reference-lost, left-empty), blocked descendants, and atomic family outcomes. Exercise mine/theirs choices with subject and optional field, partial resolution leaving outstanding issues, edits supplying a third answer, recovery/propagation and adoption only after required settlement. Fixtures may establish reachable conflicts so model runs evaluate agent interpretation and repair rather than repeatedly generating merge permutations.
11. Vault vocabulary and presentation policy — configured levels; node-kind keys/display names/valid icons/optional palette color; relationship-kind keys/display names/optional palette color, all dash choices (solid/dashed/dotted) and arrowhead choices (filled/open/none). Cover omitted color/default presentation versus explicit policy and distinguish container body color from node-kind icon identity. Node/relationship kinds are consumer-defined vocabularies, not a closed built-in list. Missing/invalid config warnings, unknown new references, removed definitions and repair must be understood. Colors/icon spellings are vocabulary values, not separate features requiring one model run each.
12. TASK-207 configured grouping — stable config group IDs/display names, empty default, explicit unique set memberships, overlapping memberships across structural containers, no inheritance, omitted/empty equivalence and reorder/dedup normalization; display-name changes without semantic delta; independent membership propagation/reconciliation. Cover one-group CLI inspection of members, internal edges, directed boundary edges and immediate external neighbors; configured-empty versus unknown group; removed definitions and repair; hidden/collapsed members versus contextual ancestors. Use the final groups array contract, not legacy group text. Browser selection/emphasis/clear, pane-local refresh/navigation and coexistence with other presentation state remain TASK-207 runtime/browser evidence owners; connect that evidence to grouping coverage rather than claiming an authored JSON file proves the viewer behavior.
13. System-owned document state — board/schema identity, kind/version/timestamps, variant IDs/parent/current/lifecycle, adoption from/at and reconciliation against/atVersion/base/issues/blockedBy are observed outcomes of real operations, never fields the author fabricates. Deterministic harness checks own metadata/coherence; Astra owns correct interpretation and truthful architectural decisions. Schema refinements and cross-reference rules need runtime evidence rather than schema-shape coverage alone.

Coverage accounting: retain schema path/field or union branch, scenario ID, expected use, evidence artifact and owner for each entry. No user-facing semantic feature or closed behavioral enum branch may remain unmapped. Account for internal metadata separately and cite its runtime owner. All required feature checks must pass; report incomplete coverage explicitly. This is a behavioral coverage inventory, not tests that read or match source-file contents.

14. Authoring constraints and recovery — account for strict unknown-field rejection, bounded/single-line names/responsibilities/labels/handles, description limits, ambiguous name references versus IDs, dangling or wrong-kind references, containment cycles, cross-subject identity collisions, participant membership, empty selections and empty walkthroughs, and invalid traffic/repeat values. These are schema/integrity behaviors, not extra decorative board features. Reuse cheap existing runtime validation owners for mechanical limits; add scenario recovery expectations where an agent must interpret a refusal and repair meaning. Cover default versus explicit values and partial traffic overrides without a combinatorial model-test matrix. A named view and an omitted view must not be conflated with the first available view.

Audit cross-check: source currently still has the legacy singular group field; TASK-207 is a planned replacement. Generated schemas, fixture contracts and feature expectations must agree on the final implementation revision. Inventory schema primitives and coherence rules as well as object fields, and keep all future coverage claims tied to actual executed evidence.

Comparison-specific distinctions from lib/compare.ts must be included in checklist expectations: emphasis is authored presentation intent but excluded from semantic change badges, whereas effective traffic is included. Board-owned views are not variant semantic changes. Participant column order is visible presentation intent but participants compare as a set; beat subjects also compare as a set. Step/beat sequence position is meaningful, with nested subjects compared independently of their flow/walkthrough. Preserve a continuing beat ID within its existing walkthrough; an omitted beat ID creates a new beat, and a beat ID from another walkthrough is refused. Cover same-batch forward parent references/handles. Keep these read/comparison rules distinct from ingress edge-identity replacement rules, which count authored property changes under their own contract.

Grader execution contract: one gpt-6-astra grader at high reasoning grades ALL scenario runs and repetitions for BOTH skill versions in one shared Codex session per comparison batch. It builds and reuses its understanding of the pinned Flask revisions rather than starting fresh per eval. The grader prompt must explicitly say: "Do not use subagents. Inspect the source and grade every run yourself in this session." Do not fan out grading or delegate code interpretation. Author runs remain parallel and isolated. Retain anonymous run IDs and withhold baseline/candidate labels from this shared grader; provide revision identity where needed for correct source interpretation. Return separate feature checklists, quality scores and evidence for every run, and account for shared grader usage separately from author usage.
