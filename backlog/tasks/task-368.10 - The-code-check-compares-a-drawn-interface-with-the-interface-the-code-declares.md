## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The board says which children callers reach. The code says which names a module exposes: root files and package exports in TypeScript, `__all__` in Python, `public` in C#, `public` and `open` in Swift, public headers in C, C++ and Objective-C. The language adapters of TASK-367 give every definition its visibility. On 2026-09-29, 18 of the 40 names that the store's `index.ts` exports had no caller outside the store.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 An entry point bound to a definition that the code does not expose is reported, because the board draws a caller that reaches past the interface
- [x] #2 A hidden part bound to an exposed definition that an outside file uses is reported as a caller the board does not draw
- [x] #3 Exposed names that nothing outside the module uses are reported as information, not as a warning
- [x] #4 It works for TypeScript first, and for each language whose adapter gives visibility
<!-- AC:END -->

Decisions the ADRs left open:
1. A module is a directory. A container names one when bound to a directory, or to the file the language says stands for its directory (TypeScript index.ts/.tsx/.mts/.cts; Python's would be __init__.py). A container bound to another file or to a symbol names no module and is not judged (no board draws such a container with children inside its file).
2. An exports that names only built output (dist) names no file of the checkout: exposure-unknown, listed as a skip, never guessed.
3. 4. Ownership of an exposed definition is the narrowest binding (ADR 0046 bound code), as for evidence; a child owns what it or a part inside it owns.
5. A use is a reference in a file outside the module whose import leads into the module, followed with definitionSite to a definition inside it. A test file (isTestPath) is no caller, as for evidence. A use only as a type counts as a use for EXPOSED_UNUSED (the design note counted 13 types among the names) but not as a caller for CALLER_UNDRAWN (never a dependency at run time, as RELATIONSHIP_UNDRAWN).
6. C and C++ have their rule (2026-10-06, 49877d859 and 6ced36231, the review of TASK-367.09). It is C in RULES of module-exposure.ts, written in c-exposure.ts. A C or C++ module is a directory. No file stands for one, so a container names one only when it is bound to a directory. Its root files are its public headers: the headers below its `include` directory where it has one, as leveldb's include/leveldb, or else the headers directly in it whose source file, their pair (c-pairs.ts), is in the module too, as db/db_impl.h beside db/db_impl.cc. A header with no source file in the module, or in a subfolder, is the module's own. Of the two readings the brief offered, the rule uses both, in that order: a project that publishes an include directory says which headers are public, and a directory without one offers the headers of its source files to the rest of the project. A public header exposes what it declares with external linkage or none: functions, extern variables, types, enumerators, macros other than its include guard, and the public members of a class. A declaration is exposed where its code is: a prototype at its definition in the header's pair, passed on by the header as an index file passes on a re-export (withCode in module-exposure.ts). Uses from outside reach it through their includes, because the include resolver gives every use its target (inModule), so usesIn reads C and C++ callers as it reads TypeScript's. A C++ method counts for its class by its name, `shop::Store::open` for `shop::Store` (memberOf in interfaces.ts), because its code is often in another file than its class. A use that reaches a declaration whose pair defines nothing of its name is a candidate, so CALLER_UNDRAWN on it is information. Owners: module-exposure.test.ts over the fixture project c-shop, and c-check.test.ts, where a file that no part binds calls the hidden money part through money.h. So criterion 4 holds for C and C++.
