Decisions the ADR left open:
1. TypeScript evidence: a use that reaches its name through an import is resolved (the import path names the file), followed through every re-export to the defining file. A use whose first name is a module-level declaration of the same file (or a member of one, spelled through it) is a candidate, because it is matched by name. A use through a value (a parameter, a local) and a name an unresolved import brings in give no evidence until a language server resolves them (TASK-367.13). Re-exports are not uses.
2. import(), require() and an import for its side effects load the whole file at run time: call evidence to the owner of the resolved file, its symbol the specifier.
3. Ownership: the use belongs to the narrowest binding that holds its line (the symbol with the shortest definition span, else a file binding, else the deepest directory); the reached definition belongs to a symbol binding around it, else its file's binding, else the binding of a file that re-exports it (nearest the definition first), else the deepest directory. Code facts keep one reference per spelling at its first line, so a symbol-bound part is credited with a use only where that first line lies in its definition.
4. Tests below a bound directory (a test, tests, __tests__, spec or specs directory; x.test.*, x.spec.*, x_test.*, test_x files) exercise its code and are not its code at run time, so they give no evidence; a binding that names a test path keeps them. Found on the dogfood vault: 8 pieces came from store and server tests.
5. Drawn: a relationship or a flow step, either direction, between the two parts or parts that hold them (the parts' containers, not parts inside). Steps count, because a sequence board draws an interaction as a step.
6. Undrawn: one finding on the reached part (path variants.<v>.content.nodes.<id>), one piece per reaching part (a resolved one before a candidate, else the first in file order); a warning when at least one piece is resolved, information when all are candidates.
7. Backwards and unsupported judge a relationship with no anchor and both ends bound. An end skipped for a reason the answer gives (unregistered repository, ref not checked out, path ignored or never read) lists the relationship as skipped with that reason and the end's name in detail. An unavailable checkout, a missing bound path or a missing bound symbol is silent here, because it is said elsewhere. Ends that hold one another or bind the same code are skipped with the new reason ends-overlap. An end whose code, and that of the parts inside it, was read only as text is not judged, and the text-only skip says so once.
8. RELATIONSHIP_BACKWARDS carries the accepted pieces that run from the end to the start, one per pair and kind. RELATIONSHIP_UNSUPPORTED carries the pieces between the ends that its kind does not accept (such as a type import under call), and none when nothing joins them.
9. ANCHOR_MISMATCH by kind: the uses are the references with an evidence kind whose spelling is the symbol, else whose last name is its last name, one per kind. Not judged on a step, on a kind without the key, in a text file, or when the anchored file defines the symbol. A warning when a use resolves through an import, else information. The definition reason takes precedence, so an anchor gets one ANCHOR_MISMATCH at most.
10. The relationship kinds are read once per pass through the store's configuration reader (the defaults where the configuration is invalid, as everywhere) and carried on each board to check, so the route is unchanged.
11. The evidence key needs at least one kind, each once: an empty list would be a kind that nothing proves; leave the key out to accept every kind.
12. The literal RELATIONSHIP_BACKWARDS trips the repository's archboard/no-compatibility-identifiers lint rule (its pattern matches _BACKWARDS at the end). It is the finding code ADR 0046 names, so the line and the test's one constant carry a disable directive with that reason; the rule stays on.
