# Audit of TASK-549: what the canonical reader shows and what it hides

Branch `integrate/pr19` at 6ccc9596d. The head moved from 9efeb41c1 during the audit, and the last merge restored `CONTAINER_LINE_TO_OWN_PART`.

In this report, main means `origin/main` at 396bfd9ad, the commit that TASK-559 names. Local `main` (38a8da877) is 15 commits behind it. I changed no file in the checkout.

## The answer

The purpose of the work is easy identification of codebase smells, seen through Ousterhout's A Philosophy of Software Design. The reader on `integrate/pr19` does not serve that purpose yet.

Most of the facts survive in code, but the reader leads with none of them. No interface measure shows on Diagram, in the picture or in the right column. A reader reaches the measures of a module through three steps: open the module, go to About, find the Interface section. A selected module that is not open shows no interface at all.

PR 19 removed more than the two losses the owner found. It deleted `semantic inspect`. It removed interface changes from comparison and the side-by-side measures of competing proposals. It also emptied Behind. Those four are gone from both reader and CLI. The redesign of TASK-559 then moved the interface and history out of the panel and into About.

The word Ousterhout has no hit in the TASK-549 notes, `docs/design/reader-redesign.md` or `docs/design/reader-council/`. The word smell has no hit in the design record, the ADRs, `CONTEXT.md`, `PRODUCT.md` or `README.md`. The intent is written down once, at TASK-559:71, after the design was settled.

## Which reading of "tracer" the evidence supports

The evidence supports the first reading most, and the second reading fits a narrower sense. All four fit something real.

1. The tracer bullets of the three design lenses. `docs/design/design-checks.md:108` and ADR 0046:619 use the term. TASK-367.05 is the tracer bullet of the code check, TASK-368.02 of the interface lens, and TASK-369.02 of the history lens. These lenses are the Ousterhout work: deep modules, seams, information hiding and locality. Two of the three no longer exist. TASK-368.02 built `semantic inspect`, and TASK-369.02 built Behind.
2. The Trace feature, Trace onward and Trace back. The owner named these toggles as a loss, and TASK-559.22 AC #8 asks for them back.
3. The decision 32 action `Trace flow`. It exists and reaches an agent, but only with a selection or on About.
4. A slice of the notes. The 24 approved slices of `docs/design/canonical-module-tickets.md` follow the tracer-bullet ticket pattern of `.agents/skills/to-tickets/SKILL.md`. This link is my inference. The ticket file does not use the word tracer.

## Notes

### Measured

- Who removed what. The commit 5e3d2c6f4 of PR 19 removed `semantic inspect`, interface changes, side-by-side measures and Behind. It also lost the panel's Trace and engine switch.
- What the redesign moved. At 5e3d2c6f4, `ModelScopeDetails` showed the interface in the sidebar with nothing selected, and `ModelHistory` stood in the selection details. The commits 2e29428e2 and 4c4eabf80 moved both to About. TASK-559.06 and 559.15 made that move on purpose, so it is a design choice and not a silent loss.
- The `id === scope` gate is older than the redesign. PR 19 already had it at `ModelSelectionDetails.tsx:222`. Main showed the interface of any picked part.
- `docs/design/reader-redesign.md` rejects "A layout selector" in its Rejected table. The owner later reversed that in TASK-559.21.
- ADR 0045:414 says that a selection makes the inspector ask. The 549.24 note says "History reads remain on demand". The code follows the note, so the ADR and the note disagree.
- ADR 0044:171 says that the answer lists the parts behind each count. Neither main's pane nor this reader lists hidden parts. With `semantic inspect` gone, no surface lists them.
- The consumer skill lost the lenses. At `BASE:`, `skills/archboard/references/read.md:22` and `propose-compare.md:179` teach inspect and footprint. At this head, `model locality` and `model footprint` have no hit under `skills/archboard` or `skills/archboard-dev`.
- This repository at TASK-549.24 acceptance gave no code warnings, 34 information findings and 15 limits. So the picture shows no finding mark here, and every finding needs a selection.

### Inferred

- `semantic inspect` left with the board commands, and nobody listed it as a loss. The TASK-549 decisions do not name it. Its removal looks like a side effect, not a decision.
- `compareInterfaces` survives with a test as its only caller, so the removal looks unintended.
- The move to About fixed the owner's overload complaint, but it also moved the one thing the work exists to show. The owner's TASK-559.22 AC7 agrees with that reading.

### Not measured or not found

- I ran no server and drew no picture. Every status comes from reading code and tasks.
- The dense grid source names no entry point rule. I did not measure whether a dense reading keeps entry points in the first row.
- Not found: a decision on temporal decomposition, on general versus special purpose, or on conjoined methods.
- Not found: a reader statement that no code pass exists for the shown revision. If no pass matches, `ModelCodeWarnings` returns nothing.

## How far the reader serves the purpose

On the picture without asking, a reader sees shape: containment, entry points in a first row, doors and line weight. That is real evidence, and the redesign made it easier to read. It shows a seam and a dependency. It gives no count and points at nothing.

In the right column, a reader sees a description, relationship lists and findings for a selected subject. No interface or history fact stands there.

The steps to each smell fact, measured from the code:

- Interface of a module: open it, go to About, find Interface. A selected module that is not open has no path.
- Unjoined pair of a module: select it, go to About, find Code history, press the button, read each partner row.
- Which modules change most: CLI only.
- What a proposal does to an interface: no path.

So the reader answers "what is this module" well. It answers "where does this design smell" only for a person who already knows where to look. On this repository the picture also carries no finding marks, because the code check gives no warnings.

## Smallest set of changes, ranked

Every change shows a count or a list. None adds a score, a color scale, a warning, or the words deep, shallow or smell to the picture, so ADR 0044 holds.

1. Put one measures line in the right column for an open or selected module. Derive the interface for any selected container in place of the `id === scope` gate. This is TASK-559.22 AC7. It is the one change that puts the lens on Diagram.
2. Restore Trace onward and Trace back in the column. This is TASK-559.22 AC8. It needs a control only, because `use-lighting.ts:86` already draws it.

4. Read history on selection, as ADR 0045:414 says, and add a model-wide list in About: hotspots and unjoined pairs. The server already answers for every part at once, so `LocalityAnswer` holds both.
5. Give agents the lens back: `model inspect`, interface changes and measures in `model compare`, and `model locality` and `model footprint` in the consumer skill. The derivations exist, so this is wiring and skill text.
6. Lead the proposal change list with interface changes. `compareInterfaces` has the answer. This comes after rank 5 because both share the same output.
7. Show findings for the open scope in the column, information findings included. If no pass exists for the revision, say so. Keep the rule of ADR 0046 that a pane starts no pass.
8. Show the measures of competing proposals side by side. This restores design it twice.
9. Decide Behind: rewire `createBehindReading` for canonical models, or delete it and the `behind` field. The present `behind: []` promises a reading that never comes.
