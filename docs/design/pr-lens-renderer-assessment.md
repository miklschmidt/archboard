# PR Lens renderer assessment

Date: 2026-09-11

The agreed product boundaries are recorded in
[ADR 0023](../adr/0023-semantic-boards-own-meaning-renderers-own-presentation.md).
Legacy files will be preserved, migration is deferred, native Obsidian compatibility
is dropped, and large diagrams navigated through pan and zoom are acceptable.

Question: should Archboard use or fork the renderer and schema in the sibling `pr-lens`
checkout to replace Excalidraw?

Inspected revisions: Archboard `bfe9382e0a1dbc55225e092f8090d310bcea46f0`; PR Lens
`0993b4dec8ae73f5e000370e6a758cdd8aa2bfd0`. The PR Lens tree was clean. Its dependencies
were not installed, so this is a source, fixture, and rendered-artifact assessment; I did not claim
a successful build or test run.

## Recommendation

Explore replacing Excalidraw with a semantic board and renderer-owned presentation. PR Lens is a
concrete starting point for that renderer and a useful schema reference. Its exact `GraphDoc`
contract should be judged against Archboard's domain before adopting it as persisted truth.

The user clarified on 2026-09-11 that their human editing has been correcting agent rendering and
organization mistakes. Free drawing has supplied little value; agents produce diagrams with weak
visual and typographic hierarchy. This changes the initial assessment, which treated preserving
spatial authoring as a product requirement. Avoiding that repair work is the observable benefit of
moving layout and styling into one renderer.

Agents should state architectural units, relationships, containment, bindings, and the subject of a
view. The renderer should choose coordinates, routing, shapes, spacing, typography, and visual
emphasis from that meaning. A renderer improvement can then improve existing boards without agents
redrawing them. Human corrections should update meaning or view intent where needed. Do not recreate
a general drawing editor merely to preserve features whose only use was fixing generated pictures.

The smallest useful experiment now tests the replacement direction:

1. Express a real current/proposed architecture in a semantic document, retaining the relationships,
   containment, code bindings, and abstraction levels the explanation needs.
2. Use PR Lens to render it, recording where its schema or fixed lane grammar loses that meaning.
3. Change presentation in the renderer without rewriting the architecture; verify hierarchy and
   readability on the real example, including a small subsequent graph change.
4. Use those concrete gaps to decide between consuming the package and forking its renderer/schema.

This could eliminate promotion and some geometry-based inference instead of rebuilding them. That
simplification is a design hypothesis to verify. Stable identity, note authority, versions, claims,
code bindings, and comparisons remain valuable independently of Excalidraw. Native Obsidian drawing
compatibility is dropped; legacy files are preserved and migration mechanisms deferred.

## Existing contracts affected by replacement

Archboard defines its product as people and agents drawing, rearranging, and reading rearrangement
back ([CONTEXT.md:1-5](../../CONTEXT.md#L1-L5)). Its comparison treats cluster membership,
containment, explicit Excalidraw groups, relative regions, inter-node direction, and prominence as
semantic signals ([compare.ts:20-45](../../src/runtime/engine/compare.ts#L20-L45)). PR Lens layout
would compute over those choices and preserve none of them automatically.

Archboard also deliberately persists Excalidraw's native element format so the note is both the
board and an Obsidian-openable artifact ([ADR 0015:36-50](../adr/0015-the-vault-is-the-truth-and-the-agent-shape-is-input.md#L36-L50)). Native elements include
rectangles, ellipses, diamonds, arrows, text, lines, free draw, and images
([vendor-types.ts:45-73](../../src/shared/board-elements/lib/vendor-types.ts#L45-L73)). Its metadata
round-trips human links and `customData.archboard`, including cross-repository code bindings
([DESIGN.md:126-159](../../DESIGN.md#L126-L159)). `GraphDoc` has no equivalent open metadata or
arbitrary element channel.

The current server renderer can export PNG and SVG, crop focused regions, embed images, verify actual
fonts, and convert Mermaid into editable Excalidraw skeletons
([browser.ts:226-282](../../src/server/board-rendering/lib/browser.ts#L226-L282)). Archboard's
headless text measurement reproduces Chrome/Excalidraw shaping to within its recorded tolerance
([measure-text.ts:1-28](../../src/runtime/engine/measure-text.ts#L1-L28)); PR Lens estimates width
from a glyph table with deliberate slack ([text.ts:3-7](https://github.com/coldteadotai/pr-lens/blob/0993b4dec8ae73f5e000370e6a758cdd8aa2bfd0/packages/renderer/src/text.ts#L3-L7)). Replacing this path
would require explicitly retaining or retiring each needed output capability. These are migration
costs, not requirements to preserve all of the current drawing product.

## Adoption choices and effort

| Choice                                   | Estimated effort                                           | Result and risk                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use renderer as a transient projection   | Medium                                                     | One adapter plus server rendering and display. Preserves the board and directly tests visual value. The renderer package's root re-exports hashing code backed by `node:crypto` ([index.ts:21-30](https://github.com/coldteadotai/pr-lens/blob/0993b4dec8ae73f5e000370e6a758cdd8aa2bfd0/packages/renderer/src/index.ts#L21-L30), [manifest.ts:1-24](https://github.com/coldteadotai/pr-lens/blob/0993b4dec8ae73f5e000370e6a758cdd8aa2bfd0/packages/renderer/src/manifest.ts#L1-L24)), so treat direct browser import as an integration question and prefer the server first. |
| Adopt selected ideas                     | Small to medium per idea                                   | Delta colours, the atlas contract, stable lane/rank hints, or patch target checks can be adopted independently when a concrete workflow needs them.                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Fork renderer after prototype            | Large and ongoing                                          | Justified only by proven presentation requirements such as Archboard-specific kinds, links, or visual grammar. A fork owns routing, layout, accessibility, SVG safety, and upstream drift.                                                                                                                                                                                                                                                                                                                                                                                   |
| Replace Excalidraw with a semantic board | Substantial migration; scope depends on retained workflows | Requires semantic persistence, agent writes, comparison, code-binding interaction, rendering, and reconciliation. Free drawing, arbitrary content, spatial inference, and a full drawing editor need not be rebuilt. Judge `GraphDoc` against these workflows before choosing it as the stored contract.                                                                                                                                                                                                                                                                     |

The checkout contains 178 commits spanning 2026-08-20 through 2026-09-11, five versioned packages,
32 test files, renderer goldens, and current showcase artifacts. It has no checked-in GitHub Actions
workflow. These are facts. The reasonable inference is active, thoughtfully tested, externally
packaged software that is still young and pre-1.0; the checkout alone does not establish adoption,
API stability, or production operating history. That maturity profile favours consuming a pinned
package behind a small adapter before accepting either a fork or a foundational schema dependency.
