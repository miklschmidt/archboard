## The model

<dl class="terms">
	<dt>Vault</dt>
	<dd>
		The `.archboard/vault` directory at the root of a checkout. Because it lives in Git, reviewers
		see model changes in the same diff as code changes.
	</dd>
	<dt>Model</dt>
	<dd>
		The complete architecture stored in a vault: modules, relationships, flows, walkthroughs, and
		active proposals. Every diagram is derived from this model.
	</dd>
	<dt>Module</dt>
	<dd>
		A named architectural responsibility with a stable identity. A module can contain child modules
		(parts) to any depth. Containment has no fixed layers.
	</dd>
	<dt>Relationship</dt>
	<dd>
		A directed connection owned by a source module and pointing to a target module. Each
		relationship has a kind (how it travels, such as `sync`, `async`, `http`, or `queue`) and an
		effect (`mutation`, `query`, or `compute`, or omitted on a declared-only `dependency`).
	</dd>
	<dt>Qualified identity</dt>
	<dd>
		The permanent ID of a module, relationship, flow, or step (for example, `Shop#Gateway`).
		Renaming a subject keeps its identity, and its former name still resolves to it.
	</dd>
	<dt>Reading</dt>
	<dd>
		A view specification describing what to render: state, scope, expanded modules, focus, lens,
		filters, and grammar. Readings copy no model data and are composed on demand.
	</dd>
</dl>

## Flows

<dl class="terms">
	<dt>Flow</dt>
	<dd>
		A single request, background job, or event modeled as an ordered exchange between modules, with
		a summary explaining what it does and why it matters.
	</dd>
	<dt>Step</dt>
	<dd>
		One item in a flow: a message (`sync`, `return`, `async`, or `self`), a decision with
		alternatives, or a loop.
	</dd>
	<dt>Grammar</dt>
	<dd>
		The diagram format for a reading: `architecture` renders modules and relationships, while
		`sequence` and `flowchart` render a single flow.
	</dd>
</dl>

## States and proposals

<dl class="terms">
	<dt>State</dt>
	<dd>
		A named version of the full model in one lifecycle phase: current, draft, historical, or
		shelved. A state keeps its identity across lifecycle changes.
	</dd>
	<dt>Current</dt>
	<dd>
		The single state describing implemented architecture. A new planning model has no current state
		until a proposal is adopted.
	</dd>
	<dt>Proposal</dt>
	<dd>
		A draft state representing planned changes that are not yet implemented, stored as diffs against
		its predecessor state.
	</dd>
	<dt>Comparison</dt>
	<dd>
		A diff between two states matched by subject identity. Interface changes appear first because
		they affect every caller.
	</dd>
	<dt>Adoption</dt>
	<dd>
		Promoting a proposal to become the current state with a recorded reason. The previous current
		state stays in history. Merging a Git branch never adopts a proposal automatically.
	</dd>
	<dt>Checkpoint</dt>
	<dd>
		An immutable Git-backed snapshot of the model's authored inputs. Shared walkthroughs and video
		recordings reference a specific checkpoint.
	</dd>
	<dt>Claim</dt>
	<dd>
		A visible status marker showing which writer is currently modifying specific subjects and why.
		Every open browser pane displays active claims.
	</dd>
</dl>

## Code and evidence

<dl class="terms">
	<dt>Binding</dt>
	<dd>
		A module's primary source location: a repository identity, a file or directory path, and an
		optional symbol. Bindings store no absolute local paths, so they resolve on every machine.
	</dd>
	<dt>Repository identity</dt>
	<dd>
		A machine-independent repository name derived from the checkout's `origin` remote, such as
		`github.com/acme/payments`. Run `archboard repo add` to register a local checkout for it.
	</dd>
	<dt>Anchor</dt>
	<dd>
		A specific source location (repository, file, and symbol) cited as proof of a relationship or
		flow step. The code check verifies anchors against the codebase.
	</dd>
	<dt>Evidence</dt>
	<dd>
		Static proof extracted from code or infrastructure showing how two modules interact: a call,
		configured path, permission, import, build dependency, or provisioning reference.
	</dd>
	<dt>Configured path</dt>
	<dd>
		Cross-network evidence linking code to infrastructure. Application code reads an environment
		variable, and a Kubernetes manifest, Compose file, or Terraform resource sets it to another
		module's address.
	</dd>
	<dt>Resolved and candidate</dt>
	<dd>
		Resolved evidence identifies its target definitively through a language server or static syntax.
		Candidate evidence matches by name alone and produces only information-level findings, never
		warnings.
	</dd>
</dl>

## Checks and findings

<dl class="terms">
	<dt>Semantics check</dt>
	<dd>
		Validates the model against the vault's vocabulary and structural rules without reading source
		code. Its errors and warnings are diagnostics.
	</dd>
	<dt>Code check</dt>
	<dd>
		Compares a model state against the code and infrastructure referenced by its bindings and
		anchors, reporting findings with file and line evidence.
	</dd>
	<dt>Embeds check</dt>
	<dd>
		Compares Git-tracked Archboard diagrams against the current model and reports any that are out
		of date.
	</dd>
	<dt>Finding</dt>
	<dd>
		An issue reported by the code check for a module, relationship, or flow step. Warnings fail the
		check. Information-level findings do not.
	</dd>
	<dt>Skip</dt>
	<dd>
		An item the check could not inspect, along with the reason (such as a missing language server).
		Skips are listed explicitly so unread code is never mistaken for clean code.
	</dd>
</dl>

## Sharing

<dl class="terms">
	<dt>Embed</dt>
	<dd>
		A Git-tracked SVG or PNG diagram generated by Archboard for a README or ADR. Each embed stores
		its render recipe so `archboard check embeds --fix` can regenerate it.
	</dd>
	<dt>Walkthrough</dt>
	<dd>
		An ordered tour of readings where each beat has a title and narrative. You can narrate
		walkthroughs with Codex in the browser or export them as video with `model record`.
	</dd>
</dl>
