Platform teams often keep Kubernetes manifests, Helm charts, and Terraform configurations in a separate repository from application code. Answering which services call each other requires reading both. A single Archboard model can bind modules across both repositories, and one `archboard check code` run validates both.

## How the check traces network hops

When a service reads a peer address from an environment variable and the infrastructure sets that variable to another service's address, the code check connects both halves into `configured-path` evidence:

<Steps>

1. **Application code.** Bound code reads an environment variable, such as `process.env.BILLING_URL` in TypeScript.
2. **Infrastructure configuration.** The Kubernetes workload, Compose service, or Terraform resource running that code sets the variable directly or through a ConfigMap loaded with `envFrom`.
3. **Target service.** The variable's value resolves to another bound module's workload, such as the Kubernetes Service `billing`.

</Steps>

When all three pieces match, the check confirms the cross-network call and verifies it against the relationships in your model.

## The relay example

[`archboard-relay-example`](https://github.com/miklschmidt/archboard-relay-example) is a four-service parcel system whose TypeScript code and Archboard model live in one repository, while its Kubernetes manifests and OpenTofu queue definitions live in [`archboard-relay-example-infra`](https://github.com/miklschmidt/archboard-relay-example-infra). Its model declares that Intake never calls Billing.

A shared ConfigMap exposes peer addresses to every workload:

```yaml title="deploy/kubernetes/peer-endpoints.yaml"
apiVersion: v1
kind: ConfigMap
metadata:
  name: peer-endpoints
data:
  CATALOG_URL: http://catalog.harbor.svc.cluster.local:8080
  DISPATCH_JOBS_URL: http://dispatch-jobs.harbor.svc.cluster.local:9324
  BILLING_URL: http://billing.harbor.svc.cluster.local:8080
```

A pull request in the application repository updates Intake to read and call `BILLING_URL`:

## Register both checkouts

Bindings identify repositories by repository identity (derived from each checkout's `origin` remote). Register both local checkouts so Archboard knows where to read their files:

<Steps>

1. Clone both repositories side by side.

   ```bash
   git clone https://github.com/miklschmidt/archboard-relay-example
   git clone https://github.com/miklschmidt/archboard-relay-example-infra
   ```

2. Register both checkouts. The first registered checkout for a repository becomes its chosen checkout.

   ```bash
   archboard repo add archboard-relay-example
   archboard repo add archboard-relay-example-infra
   archboard repo list
   ```

3. Run the code check from the repository that holds the vault. It inspects both checkouts.

   ```bash
   cd archboard-relay-example
   archboard check code
   ```

</Steps>

In the relay example, `npm run setup` runs steps 1 and 2, while `npm run gate:break` and `npm run gate:restore` add and remove the Billing call. Run `archboard repo use <dir>` to switch the chosen checkout to another directory, such as a worktree on an infrastructure branch.

<Aside type="caution" title="Unregistered repositories are skipped, not failed">
	Bindings to repositories not registered on the machine are skipped as
	[`repository-unregistered`](../reference/findings/#repository-unregistered). Because skips never
	fail the check, running without the infrastructure checkout will pass. Inspect the `skipped` list
	or fail your script on unexpected skips, as `npm run gate:self-test` does in the example.
</Aside>

## In CI

Check out the infrastructure repository beside the application repository and pass its path in the check Action's [`repos`](../reference/actions/#check-repos) input. The Action registers it before running the check:

```yaml title=".github/workflows/architecture.yml" {7-10,16-17}
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          path: app
      - uses: actions/checkout@v5
        with:
          repository: miklschmidt/archboard-relay-example-infra
          path: platform
      - uses: miklschmidt/archboard/actions/check@{{sha}} # {{ref}}
        with:
          version: "{{version}}"
          working-directory: app
          repos: |
            platform
```

For a private infrastructure repository, pass a read-access token in the second checkout's `token` input.

## Limits of cross-network evidence

The code check performs static file analysis only. It never runs the system, so it detects network hops only when source and infrastructure files declare both sides.

- **Both sides must be static.** Code must read the environment variable by literal name, and infrastructure must set that name to another module's address. Dynamically built URLs or values fetched from a secret store leave no static evidence.
- **One side alone produces an information finding.** If infrastructure sets a variable that code never reads, or code reads a variable nothing sets, a modeled relationship gets [`RELATIONSHIP_UNSUPPORTED`](../reference/findings/#relationship-unsupported) with `missing` naming the absent side. It does not fail the check.
- **Direct workload `env` counts for the whole workload.** An environment variable set directly in a Deployment's `env` counts as evidence for that Deployment even if no code reads it. Variables loaded from a ConfigMap via `envFrom` count only when bound code reads them. That is why the relay example uses a ConfigMap.
- **Ambiguous targets stay candidates.** When multiple workloads can answer the same address, the evidence is marked as a candidate and any finding stays at information severity.
- **Skipped targets are always reported.** Unregistered repositories, remote Terraform modules, and unparseable files appear under `skipped` with a reason so unchecked code is never treated as clean.
- **No live state or credentials are used.** The check never runs `terraform`, `tofu`, or `kubectl`, and never reads Terraform state, variable files, or `.terraform`. To inspect remote Terraform modules, export plan JSON with `tofu show -json` and pass it with `--plan`.
- **Terraform nested blocks and whole-resource child parts.** A part or anchor can bind a unique depth-1 named nested block of a `resource` using `<resource_address>.<block_type>["<name>"]` (such as `azurerm_application_gateway.ingress.http_listener["device-https"]`). A 1-hop intra-resource name-linked sibling block (such as `request_routing_rule["device"]`) supports anchors without emitting `configured-path` evidence, while citing the whole enclosing resource warns [`ANCHOR_MISMATCH`](../reference/findings/#anchor-mismatch). A nested-block binding is not a runner. When a resource is modeled as a container with parts inside it, at most one direct child may share its parent container's infrastructure address without triggering [`BINDING_SHARED`](../reference/findings/#binding-shared), owning unallocated whole-resource references. Unmatched nested selectors backed by `dynamic` blocks, computed `name` attributes, or `--plan`-only remote resources skip as [`expression-not-followed`](../reference/findings/#expression-not-followed) without reading `constant_value`.

## Mapping multiple repositories

One vault can bind to any number of repositories. If no single application repository owns the full system, place the vault in a dedicated repository (such as a platform repository or Home Repo) and register the remaining checkouts. See [`INSTALL.md`](https://github.com/miklschmidt/archboard/blob/main/INSTALL.md#4-how-a-command-finds-its-vault) for vault discovery rules and [Archboard in a Home Repo](../home-repo/) for a complete multi-repo setup.
