A plain diff is the wrong level for an architectural change. A reviewer sees forty changed lines and not that Intake now calls Billing. Two GitHub Actions put the architecture on the pull request. Both run only commands of the published CLI.

| Action                                       | What the reviewer gets                                                          | Permissions                               |
| -------------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------- |
| `miklschmidt/archboard/actions/check`        | Each finding as an annotation on the changed line, and a job summary            | `contents: read`                          |
| `miklschmidt/archboard/actions/pull-request` | One comment with the proposal, the pictures before and after, and the footprint | `contents: write`, `pull-requests: write` |

## Findings on the diff

The check Action turns each finding into a GitHub annotation on the file and line of its evidence. A finding that crosses a network hop has evidence in two files: the line of code that reads the address, and the line of the manifest that sets it. Each end in the pull request's repository gets an annotation. GitHub cannot put an annotation on a file of another repository, so every annotation names both ends with an excerpt of each, and the reviewer reads the whole connection from one place.

```yaml title=".github/workflows/architecture.yml"
name: architecture
on: pull_request

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: miklschmidt/archboard/actions/check@main
        with:
          version: 0.1.0
```

In the relay example, the code is in one repository and the manifest is in another. The annotation on `services/intake/src/accept.ts` line 51 reads:

```text title="RELATIONSHIP_UNDRAWN: Rate card"
The code of "Accept parcel" reaches "Rate card". No relationship joins these modules. Add the relationship between the parts that make and answer the call. If this dependency is unintended, change the code.
Evidence:
- configured-path, resolved: services/intake/src/accept.ts:51 in github.com/miklschmidt/archboard-relay-example (BILLING_URL)
      50 |   // gate:break start
    > 51 |   const billingUrl = trimUrl(process.env.BILLING_URL ?? "");
      52 |   await deps.fetch(`${billingUrl}/surcharges?routeCode=${encodeURIComponent(routeBody.routeCode)}`);
- configured-path, resolved: deploy/kubernetes/peer-endpoints.yaml:13 in github.com/miklschmidt/archboard-relay-example-infra (BILLING_URL)
      12 |   DISPATCH_JOBS_URL: http://dispatch-jobs.harbor.svc.cluster.local:9324
    > 13 |   BILLING_URL: http://billing.harbor.svc.cluster.local:8080
      14 |
```

The job summary lists up to 100 findings, evidence for the first 30 errors and warnings, and the skipped subjects. Each code links to [its explanation](../reference/findings/). GitHub shows at most ten annotations of each level for one step. The Action saves the complete JSON report at its `report` output. Upload that file as an artifact to keep the complete list for review.

### Decide what blocks

| Input              | Effect                                                                       |
| ------------------ | ---------------------------------------------------------------------------- |
| `fail-on: warning` | The default. The job fails while a warning or a semantic diagnostic remains. |
| `fail-on: never`   | The findings show, and the job never fails on them.                          |
| `allow-codes`      | These codes show and never fail the job, such as `CALLER_UNDRAWN`.           |

A check that cannot run fails the job in every case: a usage error, a refusal or an unreachable server.

## The plan on the pull request

An agent that plans a change first writes it as a proposal: the architecture after the change, beside the current one. The pull-request Action finds that proposal and posts one comment. It updates the same comment on each push. [Pull request #2 of the relay example](https://github.com/miklschmidt/archboard-relay-example/pull/2) makes the same call to Billing with a plan, and its comment shows each part below.

<Steps>

1. **The proposal.** Its name and summary, and what it adds, removes and changes.
2. **Before and after.** The current architecture at the base commit, and the proposal at the head commit, as SVG in the reader's light or dark theme.
3. **The footprint.** The modules whose code the pull request changed, in three groups: planned and changed, changed outside the plan, and planned but unchanged.
4. **The map.** A link to the full-size picture and to the vault at the head commit.

</Steps>

```yaml title=".github/workflows/pull-request.yml"
name: pull-request
on:
  pull_request:
    types: [opened, edited, synchronize, reopened, labeled, unlabeled]

permissions:
  contents: write
  pull-requests: write

jobs:
  report:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
      - uses: miklschmidt/archboard/actions/pull-request@main
        with:
          version: 0.1.0
          out-of-plan: warn
```

`fetch-depth: 0` is required, because the Action reads the base and the head from Git history. The `labeled` and `unlabeled` events let the override label below take effect at once, and `edited` runs the Action again when the marker in the description changes.

### How it finds the proposal

The Action takes the first of these that it finds:

<Steps>

1. The `state` input, by identity or name.
2. The marker that the `archboard-pr` skill writes into the pull request's description:

   ```html
   <!-- archboard-pr model="rpmPjlm0" state="zu80HRHt" -->
   ```

3. The only draft proposal of the model.

</Steps>

With none, the comment shows the architecture before and after and the changed modules, and judges nothing against a plan.

The plan is what the proposal changes against the current architecture at the base, as the pictures show: each module that it adds, removes or changes, and both ends of each relationship or flow step that it adds, removes or changes. This holds for a draft and for a proposal that the branch already adopted, as the skill does once the code matches it.

### Changes outside the plan

The footprint's middle group is the interesting one: modules whose code changed although the plan did not name them. `out-of-plan` says what happens then.

| `out-of-plan` | Effect                                                                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `warn`        | The default. An annotation and a line in the comment.                                                                                                                           |
| `fail`        | The job fails, and it also fails when the plan cannot be checked. The label `archboard: out of plan` lets the pull request through, and the comment says that the label did it. |
| `off`         | The footprint shows, and nothing is judged.                                                                                                                                     |

Change the label with `override-label`. A pull request with no proposal has no plan, so nothing in it is out of plan. Removing the marker from the description therefore turns the plan check off for that pull request.

### Where the pictures live

GitHub shows an image in a comment only from an address on the web. The Action commits the SVGs to an orphan branch, `archboard-assets`, under `pr-<number>/<head commit>/`, and links them from there. It removes the folders of older commits of the same pull request. A pull request from a fork gets a read-only token, so its comment comes without pictures and says why.

<Aside type="caution" title="Private repositories">
	An image on `raw.githubusercontent.com` of a private repository needs the reader's sign-in, and
	GitHub does not always pass it to a comment. The comment then shows the links in place of the
	pictures.
</Aside>

## Explain the change in the description

The comment states facts. The `archboard-pr` skill, which `archboard init` installs, has your agent write the description around them: the problem, the resulting behavior, the evidence and the merge danger. Ask for it when you open the pull request:

```text title="Ask your agent"
Open a pull request for this branch. Use the archboard-pr skill: plan the change as a proposal,
adopt it on this branch once the code matches, and explain the architecture in the description.
```
