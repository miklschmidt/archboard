A line-by-line diff hides architectural impact: a reviewer can read forty changed lines without noticing that Intake now calls Billing. Two GitHub Actions surface architecture changes on every pull request using only the published CLI.

| Action                                       | What the reviewer gets                                                 | Permissions                              |
| -------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------- |
| `miklschmidt/archboard/actions/check`        | Inline diff annotations for each finding, plus a job summary           | `contents: read`                         |
| `miklschmidt/archboard/actions/pull-request` | Pull request comment with the proposal, code footprint, and plan check | `contents: read`, `pull-requests: write` |

## Findings on the diff

The check Action adds a GitHub annotation on the file and line for each finding's evidence. When a finding spans a network hop (code in one file, manifest in another), every end inside the pull request's repository receives an annotation.

Because GitHub cannot annotate files in another repository, each annotation includes excerpts from both ends so reviewers can inspect the full connection in one place.

```yaml title=".github/workflows/architecture.yml"
name: architecture
on: pull_request

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 22
      # The checkout's own TypeScript is the default TypeScript server.
      - run: npm ci
      # A server for each other language in .archboard/language-servers.json.
      - run: pip install pyright
      - uses: miklschmidt/archboard/actions/check@{{sha}} # {{ref}}
        with:
          version: "{{version}}"
```

Install project dependencies and language servers before running the check Action, because symbol resolution requires a language server. See [Run checks as a gate](../gate/#in-ci) for setup details. Without a language server, unresolved references stay at information severity.

In the relay example, application code and Kubernetes manifests live in separate repositories. The annotation on `services/intake/src/accept.ts` line 51 shows both ends:

```text title="RELATIONSHIP_UNDRAWN: Rate card"
The code of "Accept parcel" reaches "Rate card". No relationship joins these modules. Add the relationship between the parts that make and answer the call. If this dependency is unintended, change the code.
Evidence:
- configured-path, resolved: services/intake/src/accept.ts:51 in github.com/miklschmidt/archboard-relay-example (BILLING_URL)
      50 |   // gate:break start
    > 51 |   const billingUrl = trimUrl(process.env.BILLING_URL ?? "");
      52 |   await deps.fetch(`${billingUrl}/surcharges?routeCode=${encodeURIComponent(routeBody.routeCode)}`);
- configured-path, resolved: deploy/kubernetes/peer-endpoints.yaml:13 in github.com/miklschmidt/archboard-relay-example-infra (BILLING_URL)
      12 |   DISPATCH_JOBS_URL: http://dispatch-jobs.harbor.svc.cluster.local:9324
    > 13 |   BILLING_URL: http://billing.harbor.svc.cluster.local:8080
      14 |
```

The job summary lists up to {reference.facts.summaryRows} findings, shows evidence for the first {reference.facts.summaryDetails} errors and warnings, and lists skipped subjects. Each code links to the [Check findings reference](../reference/findings/). Because GitHub displays at most {reference.facts.annotationsPerLevel} annotations per severity level in a step, upload the Action's [`report`](../reference/actions/#check-report) output file as an artifact to preserve the complete JSON report.

### Decide what blocks

| Input                                                     | Effect                                                                                                             |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| [`fail-on: warning`](../reference/actions/#check-fail-on) | The default. Fails the job if any warning or semantic diagnostic is reported.                                      |
| [`fail-on: never`](../reference/actions/#check-fail-on)   | Reports findings in annotations and the job summary without failing the job.                                       |
| [`allow-codes`](../reference/actions/#check-allow-codes)  | Lists finding codes (such as [`CALLER_UNDRAWN`](../reference/findings/#caller-undrawn)) to report without failing. |

Module-depth severities (such as [`EXPOSED_VALUE`](../reference/findings/#exposed-value)) are controlled in the vault configuration and apply consistently across the CLI, Measures, and the GitHub Action. Without custom rules, upgrading enables module-depth warnings across all modules, including [`MODULE_SHALLOW`](../reference/findings/#module-shallow). Use [debt mode](../gate/#fail-on-a-shallow-module) to fail only on shallow modules touched by the pull request. To lower a rule across the repository, configure `codeCheck.rules`: setting a code to information keeps findings visible without failing (unless debt mode promotes a touched shallow module to a warning), while `"off"` removes it from annotations and job summaries:

```yaml title=".archboard/vault/.archboard/config.yaml"
codeCheck:
  rules:
    EXPOSED_VALUE: information
    CODE_PASS_THROUGH: "off"
```

See [Set the level of a module-depth rule](../gate/#set-the-level-of-a-module-depth-rule) for all seven codes and configuration constraints. Use [`allow-codes`](../reference/actions/#check-allow-codes) when you want to allow a finding only in a specific CI job.

Execution errors always fail the job regardless of [`fail-on`](../reference/actions/#check-fail-on): invalid arguments, CLI refusals, an unreachable server, or a missing vault. Set [`checks: embeds`](../reference/actions/#check-checks) if the repository has no vault and you only want to verify tracked diagrams.

## Proposal and footprint comment

Before implementing an architectural change, an agent writes a proposal describing the target architecture alongside the current state. The `pull-request` Action locates that proposal and maintains one comment on the pull request, updating it on every push. If a push removes the vault, the comment notes that as well.

[Pull request #2 of the relay example](https://github.com/miklschmidt/archboard-relay-example/pull/2) implements the Billing call with a proposal and shows all four sections below.

<Steps>

1. **Proposal.** The proposal's name, summary, and added, removed, or changed subjects.
2. **Vault.** A link to the vault at the pull request's head commit.
3. **Plan check.** Whether any module changed outside the proposal and how that affects the job status.
4. **Footprint.** Changed modules grouped into three collapsible sections with counts: changed outside the plan (expanded by default), planned and changed, and planned but unchanged. Changed files not bound to any module appear below them and are never judged as out of plan.

</Steps>

<Aside type="note" title="Planned: interactive diagrams">
	The current comment is Markdown text. A planned hosted pull request bot will add interactive
	before-and-after architecture diagrams.
</Aside>

```yaml title=".github/workflows/pull-request.yml" {4,10-12,20}
name: pull-request
on:
  pull_request:
    types: [opened, edited, synchronize, reopened, labeled, unlabeled]

permissions:
  contents: read
  pull-requests: write

concurrency:
  group: archboard-report-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  report:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
      - uses: miklschmidt/archboard/actions/pull-request@{{sha}} # {{ref}}
        with:
          version: "{{version}}"
          out-of-plan: warn
```

`fetch-depth: 0` is required so the Action can read both the base and head commits from Git history. The `concurrency` group cancels superseded runs on new pushes, and any stale run that finishes later skips posting. Listening to `labeled` and `unlabeled` applies the override label immediately, and `edited` re-runs the check if the description marker changes.

### How the Action selects a proposal

The Action selects the first match in this order:

<Steps>

1. The [`state`](../reference/actions/#pull-request-state) input, by ID or name.
2. An HTML comment marker written into the pull request description by the `archboard-pr` skill:

   ```html
   <!-- archboard-pr model="rpmPjlm0" state="zu80HRHt" -->
   ```

3. The model's only draft proposal, if just one exists.

</Steps>

If none matches, the comment lists the changed modules without comparing them against a plan, as in [pull request #1 of the relay example](https://github.com/miklschmidt/archboard-relay-example/pull/1).

The plan consists of everything the proposal changes relative to the base commit's current architecture: every added, removed, or changed module, plus both endpoints of every added, removed, or changed relationship or flow step. This applies both to active drafts and to proposals already adopted on the branch.

If the base commit has no vault (for example, on the pull request introducing Archboard), the base architecture is treated as empty and the plan covers every module in the proposal. If either commit's model cannot be read, the comment names the commit and prints the CLI error.

### Changes outside the plan

Modules whose bound code changed without being part of the plan appear in the out-of-plan group. A parent directory module is excluded if its `holds` list contains changed child modules that cover every modified file inside it. Older CLI versions that omit `holds` count every changed module absent from the plan. Configure the behavior with [`out-of-plan`](../reference/actions/#pull-request-out-of-plan):

| [`out-of-plan`](../reference/actions/#pull-request-out-of-plan) | Effect                                                                                                                                                                                                                                                                               |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `warn`                                                          | The default. Adds a warning annotation and notes out-of-plan modules in the comment.                                                                                                                                                                                                 |
| `fail`                                                          | Fails the job. Also fails when the plan cannot be checked (unreadable proposals or footprint, an unknown proposal name, or multiple drafts with none selected). Adding the <code>{report["override-label"]}</code> label bypasses the failure and notes the override in the comment. |
| `off`                                                           | Displays the footprint without judging out-of-plan changes.                                                                                                                                                                                                                          |

Customize the bypass label with [`override-label`](../reference/actions/#pull-request-override-label). Pull requests with no proposal have no plan and cannot fail this check. Because a single draft is selected automatically, deleting the description marker will not disable the check. Set [`out-of-plan: off`](../reference/actions/#pull-request-out-of-plan) instead. When multiple drafts exist and none is specified, the plan check cannot run.

### Added modules without new code

If a proposal adds a module whose source files already exist on the base branch, the diagram misleadingly presents existing code as newly added. The footprint flags these modules under "Added without new code". A branch counts as adding code when it introduces a new file inside the module's binding or adds the bound symbol (renaming an existing file does not count, while adding a new file inside a bound directory does). To fix this, model the existing code in the current architecture in a prerequisite pull request. Modules bound to non-existent paths appear here too and need their bindings repaired. Configure this check with [`preexisting`](../reference/actions/#pull-request-preexisting):

| [`preexisting`](../reference/actions/#pull-request-preexisting) | Effect                                                                                                                                                                                                          |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `warn`                                                          | The default. Adds a warning annotation and notes the modules in the comment.                                                                                                                                    |
| `fail`                                                          | Fails the job (including when the footprint cannot be read). The <code>{report["override-label"]}</code> label bypasses the failure, just like [`out-of-plan`](../reference/actions/#pull-request-out-of-plan). |
| `off`                                                           | Displays the group without failing or annotating.                                                                                                                                                               |

### Checking branches before a pull request

For branches merged without a pull request (such as ticket branches merging into an integration branch), run the same check locally with the CLI:

```bash
archboard model footprint --base <integration-branch> --head <ticket-branch> --state <draft> --fail-outside
```

The command exits <Exit command="model footprint" outcome="outside" /> and prints out-of-plan modules to standard error. Passing `--fail-outside` requires a draft state.

If the vault repository contains the ticket branch, `model footprint` reads the draft from that branch. Otherwise, it reads the draft from disk.

Both `archboard-plan` and `archboard-deepen` run this gate with `--model-at checkout` in the integration worktree before merging each ticket branch, because the draft edits live in the integration worktree rather than on individual ticket branches.

A module counts as changed only when its bound code differs between the merge base and the head commit. Reverted changes and changes already present in a lower layer of a merge-based stack do not count. Each changed module lists the commits that modified it.

A directory-bound module changes whenever files inside it change, but it is excluded from out-of-plan failures if changed child modules listed in its `holds` cover every modified file. The GitHub Action applies the same rule. For example, given `Workspace` bound to `libs/workspace` and `Installation` bound to `libs/workspace/src/installation.ts`:

| Changed file                         | Included in draft | Exit status                                                           |
| ------------------------------------ | ----------------- | --------------------------------------------------------------------- |
| `libs/workspace/src/installation.ts` | `Installation`    | `0` (`Workspace` changed too, and holds `Installation`)               |
| `libs/workspace/src/installation.ts` | neither           | <Exit command="model footprint" outcome="outside" /> (`Installation`) |
| `libs/workspace/README.md`           | `Installation`    | <Exit command="model footprint" outcome="outside" /> (`Workspace`)    |
| both files                           | `Installation`    | <Exit command="model footprint" outcome="outside" /> (`Workspace`)    |

Changed files not matched by any binding appear under `unboundFiles` in JSON output (with the first few printed to standard error) and never affect the exit status. Review them to decide whether to add bindings or leave them unbound.

With a draft selected, each module's `newSource` field reports whether the branch added new code for it. Passing `--fail-preexisting` exits <Exit command="model footprint" outcome="preexisting" /> if any newly added module has no new code. The `archboard-pr` skill runs this check before generating a pull request description.

### Fork pull requests and missing permissions

Pull requests from forks receive a read-only token, so GitHub blocks posting comments. In that case, or whenever the workflow omits `pull-requests: write`, the Action writes the report to the workflow job summary instead.

### Write the report to a file

Pass [`report-file`](../reference/actions/#pull-request-report-file) to write the Markdown report (including its hidden comment marker) to a file instead of posting a comment or writing a job summary. The job then needs only `contents: read`, while plan checks still emit annotations and fail the step normally. Use the [`report`](../reference/actions/#pull-request-report) output in a downstream step to publish the file wherever you need, such as appending it to the job summary:

```yaml title=".github/workflows/pull-request.yml" {17,20-24}
name: pull-request
on:
  pull_request:
    types: [opened, edited, synchronize, reopened, labeled, unlabeled]

permissions:
  contents: read

jobs:
  report:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
      - uses: miklschmidt/archboard/actions/pull-request@{{sha}} # {{ref}}
        id: architecture
        with:
          version: "{{version}}"
          report-file: ${{ runner.temp }}/architecture.md
      - if: always() && steps.architecture.outputs.report != ''
        run: cat "$REPORT" >> "$GITHUB_STEP_SUMMARY"
        env:
          REPORT: ${{ steps.architecture.outputs.report }}
```

`always()` ensures the final step runs even when the plan check fails.

Relative paths resolve from the workspace root, and missing parent directories are created automatically. If writing the file fails, the step fails and leaves [`report`](../reference/actions/#pull-request-report) empty.

## Explain the change in the PR description

The bot comment reports objective diff facts. The `archboard-pr` skill (installed by `archboard init`) guides your agent to explain the context in the pull request description: the problem, resulting behavior, supporting evidence, and merge risks. Prompt your agent when opening a pull request:

```text title="Ask your agent" wrap
Open a pull request for this branch. Use the archboard-pr skill: plan the change as a proposal,
adopt it on this branch once the code matches, and explain the architecture in the description.
```

`archboard-pr` models flowcharts and sequence diagrams as Archboard flows and renders them with `archboard model render`. Hand-written Mermaid blocks can drift from the model, so if the `archboard-pr` section of a description contains a Mermaid code block, the Action logs a warning and notes it in the comment without failing the job.
