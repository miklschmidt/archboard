A Home Repo is a central repository holding your agent skills, `AGENTS.md`, and shared documentation. You start agent sessions there, and its `AGENTS.md` points to your service repositories. Matt Pocock describes this pattern in [The Home Repo Pattern](https://www.aihero.dev/the-home-repo-pattern). Putting the Archboard vault in the Home Repo gives you a single model covering every repository in your system.

## Directory layout

```text
~/repos/acme/
├── home/                  the Home Repo
│   ├── AGENTS.md          a pointer to each other repository
│   └── .archboard/vault   one model of the whole system
├── storefront/
├── payments-api/
└── platform/
```

The service repositories do not need vaults of their own. Modules in the Home Repo bind to code in other repositories using a repository identity (from the checkout's `origin` remote, such as `github.com/acme/storefront`) and a relative path (such as `src/checkout/`). Because bindings store no absolute paths, they resolve on every machine.

## Setup

<Steps>

1. Run `archboard init` in the Home Repo to install the agent skills, create the vault, and register the Home Repo checkout.

   ```bash
   cd ~/repos/acme/home
   archboard init
   ```

2. Register local checkouts for the other repositories so the code check and browser UI can read their source files.

   ```bash
   archboard repo add ~/repos/acme/storefront
   archboard repo add ~/repos/acme/payments-api
   archboard repo add ~/repos/acme/platform
   archboard repo list
   ```

3. Ask your agent to [draw the first map](../first-map/#2-draw-the-first-map) from the Home Repo. `archboard init` creates an empty model. Bind each module to its source in the other repositories using the repository identities printed by `archboard repo list`.

4. Commit the vault in the Home Repo.

   ```bash
   git add .archboard
   git commit -m "docs(architecture): add the Archboard vault"
   ```

</Steps>

Because the checkout registry is machine-local, each developer machine registers its own checkouts. Register language servers inside each repository that holds the source code, as described in [Install and set up](../install/#set-up-the-language-servers).

## Running commands across repositories

Commands run inside the Home Repo locate `.archboard/vault` automatically. Running `model read` inside a service repository without a vault exits with `VAULT_NOT_FOUND`. If the Home Repo's model binds to that repository, the error prints the Home Repo path so you can pass it with `-C`:

```bash
archboard -C ~/repos/acme/home model read
```

In a checkout without a vault, `archboard check` skips the semantics and code checks. Pass `-C` pointing to the Home Repo to run them.

## Track cross-repository changes

Git shows which repositories have new commits, while `archboard model footprint` maps those commits to affected modules across every bound repository. Run it from the Home Repo:

```bash
archboard model footprint --base main
```

The command reads commits between `main` and `HEAD` in the chosen checkout of each repository. It lists every changed module and reports changed files with no module binding under `unboundFiles`.

Pass `--state` with a proposal name or ID to compare the commits against that plan. The output groups modules into three categories: planned and changed, changed outside the plan, and planned but unchanged. Review out-of-plan modules first. Adding `--fail-outside` exits <Exit command="model footprint" outcome="outside" /> if any modified module is outside the plan. A parent directory module is excluded if changed child modules already bind every modified file inside it. Unbound files never fail this gate.

The output also lists modules added by the draft whose source code already existed before the branch. Pass `--fail-preexisting` to exit <Exit command="model footprint" outcome="preexisting" /> when that list is non-empty, so you can model existing code in the current architecture first.

```bash
archboard model footprint --base main --state "Split payments" --fail-outside
```

If the branch already adopted its proposal into the current state, running `model footprint` without `--state` compares the head's current state against the merge base's current state whenever they differ, preserving the three groups.

<Aside type="caution" title="Every repository needs the base ref">
	Use a ref that exists in every bound checkout, such as `main` or a commit SHA. If any checkout
	cannot resolve the base or head ref, the command names that repository and exits
	<Exit command="model footprint" outcome="unread" />. The command reads only local Git objects and
	never fetches.
</Aside>

`model footprint` inspects each repository's chosen checkout shown by `archboard repo list`. If an agent committed changes in a Git worktree, switch the chosen checkout to that worktree first with `archboard repo use <dir>`.

Pass `--head` to inspect another branch. If the Home Repo holds that branch, Archboard reads the vault from that Git ref so `--state` can select branch-only proposals. If only a code repository holds that branch, Archboard reads the vault on disk. Pass `--checkpoint` to read a retained checkpoint instead.

```bash
archboard model footprint --base main --head agent/split-payments --state "Split payments"
```

The JSON field `vaultRead` records the model source: `{ "at": "checkout" }` for the working tree on disk, or `{ "at": "ref", "ref": "<head>", "commit": "<commit>" }` for a Git ref.

If you have uncommitted proposal edits on disk, add `--model-at checkout` to read the working tree instead of the committed head.

### In the browser

Open **Measures** and select **What this branch changed**. Pick the base ref, head ref, and comparison state from the searchable menus (you can also type any Git ref). The view loads when opened and refreshes when you click **Refresh**.

With a proposal selected, the view displays three cards: **Planned and changed**, **Changed outside the plan**, and **Planned, not changed yet**. Without a proposal, it shows a single **Changed** card. If the branch already adopted its proposal, **Against** displays **Current, adopted on this branch** and shows all three cards. Click a module in any card to select it in the diagram, or click the info button beside **Refresh** to inspect the read scope.

Click **Show on picture** at the bottom of a card to open the nearest shared parent of its modules (or the root reading if they have none) and select every listed module or its drawn container.

The diagram uses the model source and state shown in **Against**. When reading from a Git ref, Archboard opens a read-only branch reading whose state chip displays the ref and commit SHA, and whose URL survives page reloads.

## In CI

Because service repositories have no vault, running `archboard check` alone inside them skips model checks. Instead, check out both the service repository and the Home Repo in CI, set [`working-directory`](../reference/actions/#check-working-directory) to the Home Repo, and list the service checkout under the check Action's [`repos`](../reference/actions/#check-repos) input:

```yaml title=".github/workflows/architecture.yml" {8-12,16-18}
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          path: storefront
      - uses: actions/checkout@v5
        with:
          repository: acme/home
          path: home
          token: ${{ secrets.HOME_REPO_TOKEN }}
      - uses: miklschmidt/archboard/actions/check@{{sha}} # {{ref}}
        with:
          version: "{{version}}"
          working-directory: home
          repos: |
            storefront
```

Install the storefront's dependencies and language servers before running the check, as shown in [Run checks as a gate](../gate/#in-ci). Without a language server, unresolved calls stay at information severity and do not fail the check. A private Home Repo requires a read-access token in the second checkout step. Bindings to repositories not registered in the workflow are skipped as [`repository-unregistered`](../reference/findings/#repository-unregistered) and never fail the check. To validate the entire system in the Home Repo's own CI, check out every bound repository and list all of them under [`repos`](../reference/actions/#check-repos).

## When to keep the vault in a service repository

A Home Repo puts model updates and code updates in separate pull requests. If a single repository holds most of your system, keep the vault in that repository instead so reviewers see model and code changes in the same diff. That model can still bind to secondary repositories, as shown in [Application and infrastructure](../platform/).
