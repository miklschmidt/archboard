A Home Repo is one repository that holds your skills, your `AGENTS.md` and your shared docs. You start every agent session there, and its `AGENTS.md` points to each of your other repositories. Matt Pocock describes the pattern in [The Home Repo Pattern](https://www.aihero.dev/the-home-repo-pattern). The architecture of a system that spans those repositories is a shared doc too, so its vault goes in the Home Repo.

## The layout

```text
~/repos/acme/
├── home/                  the Home Repo
│   ├── AGENTS.md          a pointer to each other repository
│   └── .archboard/vault   one model of the whole system
├── storefront/
├── payments-api/
└── platform/
```

The other repositories have no vault. A module in the model binds to a file or a directory in any repository, by the identity of the repository and a path, such as `github.com/acme/storefront` and `src/checkout/`. The identity comes from the `origin` remote of the checkout. The binding holds no absolute path, so it resolves on every machine.

## Set it up

<Steps>

1. Run `archboard init` in the Home Repo. It installs the skills for your user, makes the vault and registers the checkout of the Home Repo.

   ```bash
   cd ~/repos/acme/home
   archboard init
   ```

2. Register a checkout of each other repository on this machine. The code check and the browser read the code of a binding from that checkout.

   ```bash
   archboard repo add ~/repos/acme/storefront
   archboard repo add ~/repos/acme/payments-api
   archboard repo add ~/repos/acme/platform
   archboard repo list
   ```

3. Ask your agent to [draw the first map](../first-map/#2-draw-the-first-map) in the Home Repo. `init` creates an empty model. Bind each module to its source in the other repositories. Use the repository identities from `archboard repo list`.

4. Commit the vault in the Home Repo.

   ```bash
   git add .archboard
   git commit -m "docs(architecture): add the Archboard vault"
   ```

</Steps>

Each machine that runs the check registers its own checkouts, because the registry belongs to the machine. Register a language server for each language in the repository that holds the code, as [Install and set up](../install/#set-up-the-language-servers) shows.

## Where the agent runs commands

A model command run in the Home Repo finds the vault without `-C`. In another repository, `model read` refuses with `VAULT_NOT_FOUND`. If the Home Repo's model binds that repository, the refusal names the Home Repo as the directory to give with `-C`:

```bash
archboard -C ~/repos/acme/home model read
```

In a checkout without a vault, `archboard check` skips the semantic and code checks. Pass `-C` to run them against the Home Repo.

## See what an agent changed

Git tells you which repositories have new commits. `archboard model footprint` tells you which modules those commits changed, in every repository that the model binds. Run it in the Home Repo:

```bash
archboard model footprint --base main
```

It reads the commits between `main` and `HEAD` in the chosen checkout of each repository. It lists each module that the commits changed. Under `unboundFiles`, it lists each changed file that no module is bound to.

If the agent worked from a proposal, select the draft with `--state`. The answer then puts modules in three groups: planned and changed, changed outside the plan, and planned but unchanged. Review the modules changed outside the plan first. `--fail-outside` exits <Exit command="model footprint" outcome="outside" /> for changed modules outside the plan. It ignores an outer directory module when changed modules inside it bind every changed file there. Unbound files never fail this gate.

```bash
archboard model footprint --base main --state "Split payments" --fail-outside
```

<Aside type="caution" title="Every repository needs the base">
	Use a ref that resolves in each checkout, such as `main` or a commit. If a repository cannot read
	the base or the head, the command names that repository and exits
	<Exit command="model footprint" outcome="unread" />. The command reads only what each checkout
	already has, and it fetches nothing.
</Aside>

The command reads one checkout of each repository, the chosen checkout. `archboard repo list` shows which checkout that is. If an agent commits in a worktree, choose that worktree first with `archboard repo use <dir>`.

To read another branch, name it with `--head`. If the Home Repo holds that branch, the command reads the model as the branch holds it, so `--state` can name a proposal that only the branch has. The answer's `vaultRead` names the model that it read. If you edited a proposal and did not commit it to the head, add `--model-at checkout` to read the model on disk.

```bash
archboard model footprint --base main --head agent/split-payments --state "Split payments"
```

### In the browser

Open Measures and choose `What this branch changed`. Choose the base, the head and the state to set the commits against. Each list is searchable, and you can type any ref. The view reads when it opens and when you press Refresh.

`Show on picture` opens the nearest module that holds a list's modules, and selects them.

It uses the model that the footprint read, in the state that Against names. If the footprint read a Git ref, it opens a branch reading: the model at that ref's commit. If only a code repository holds the head, it uses the model on disk. The state chip names a branch reading's ref and commit. A branch reading is read-only, and its address survives a reload.

## In CI

The other repositories have no vault, so their own `archboard check` has no model to read. Run the check with the vault of the Home Repo, and register the checkout of the code beside it. In the CI of a repository such as the storefront, check out both and list the code in the check Action's [`repos`](../reference/actions/#check-repos) input:

```yaml title=".github/workflows/architecture.yml" {8-12,16-18}
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          path: storefront
      - uses: actions/checkout@v5
        with:
          repository: acme/home
          path: home
          token: ${{ secrets.HOME_REPO_TOKEN }}
      - uses: miklschmidt/archboard/actions/check@{{sha}} # {{ref}}
        with:
          version: "{{version}}"
          working-directory: home
          repos: |
            storefront
```

Install the dependencies and the language servers of the storefront before the check, as [The check as a gate](../gate/#in-ci) shows. Without a language server, a call that needs resolved evidence stays information, and the check passes. A private Home Repo needs a token with read access, as the second checkout shows. A binding into a repository that the run does not register is skipped as [`repository-unregistered`](../reference/findings/#repository-unregistered). A skip never fails the check. To check the whole system in the CI of the Home Repo, check out every repository and list each one under [`repos`](../reference/actions/#check-repos).

## When the vault stays in its repository

A Home Repo puts the change to the model and the change to the code in different pull requests. If one repository holds most of the system, keep the vault in that repository. A reviewer then reads both changes in one diff, and that model can still bind into the other repositories, as [Application and infrastructure](../platform/) shows.
