Coding agents lose their understanding of a codebase when a session ends. This guide walks through creating a persistent architecture model by pairing a coding agent with an engineer who knows the system.

## Prerequisites

- A local clone of a repository your team owns.
- Archboard installed (see [Install and set up](../install/)).
- Codex or Claude Code on your `PATH` to read the codebase and write the model.
- A Codex sign-in, required only for voice narration and video recording in step 4.
- An engineer who knows the system and can verify the agent's output. The agent extracts structure from code, and the engineer validates boundaries and intent.

| Step                                | Output                                            |
| ----------------------------------- | ------------------------------------------------- |
| 1. Initialize the repository        | Vault, skills, and language servers configured    |
| 2. Draw the first map               | Root modules bound to source code                 |
| 3. Document three flows             | Three sequence diagrams backed by source anchors  |
| 4. Create an onboarding walkthrough | Narrated walkthrough and optional video recording |
| 5. Decide what fails CI             | List of finding codes that block pull requests    |

## 1. Initialize the repository

```bash
cd ~/Projects/payments-api
archboard init
```

`archboard init` installs the `archboard`, `archboard-pr`, `archboard-plan`, and `archboard-deepen` skills, creates the vault, and registers the checkout. It then launches your agent to configure language servers. Once the agent finishes, commit `.archboard`:

```bash
git add .archboard
git commit -m "docs(architecture): add the Archboard vault"
```

## 2. Draw the first map

Start with the top-level responsibilities a new engineer needs to learn first rather than mapping every file. Give your agent this prompt:

```text title="Ask your agent" wrap
Map this repository in an Archboard proposal. Start with the root modules a new engineer
must know. Explain each one's responsibility and its relationships. Bind each owned module
to the code that implements it, mark systems outside our ownership as external, and run
the checks against the proposal. Give me the proposal ID so I can review the map.
```

Run `archboard status` to print the local server URL. Open it, pick your repository, and select the draft in History. Open panes show what the agent is claiming and why. You can also open the draft at a specific module from the CLI:

```bash
archboard status
archboard browser show --pane A --state "<proposal-id>" --module "<module>"
```

Review the initial model with an engineer who knows the codebase. Check three things:

<Steps>

1. Would you skip a module when explaining the system to a new hire? Merge it into its parent or drop it.
2. Is a major responsibility missing from the model? Ask the agent to add it.
3. Does a relationship point the wrong way or connect two modules that do not interact? Ask the agent to re-read the source code and fix it.

</Steps>

Check the proposal after each round. Findings identify affected subjects or artifacts and include supporting locations when available:

```bash
archboard check --state "<proposal-id>"
```

<Aside type="tip" title="Start small">
	Seven clear modules are more useful than forty granular ones. You can decompose any module into
	child parts later, and the code check validates bindings at every level.
</Aside>

### What makes a good map

- Run [`archboard model config`](../reference/cli/model/#model-config) to see the vault's active module kinds, relationship kinds, groups, lenses, and code-check rules.
- Bind each code container to the directory that holds its parts. A leaf module can bind a directory or a recognized entry file such as `index.ts`, `__init__.py`, or `mod.rs` so the code check measures its interface and depth. Bind a smaller part to its file or symbol when that part owns a specific implementation.
- Mark systems, services, or packages outside the repository's ownership boundary `external`. Leave them unbound unless Archboard can read their vendored code in a checkout.
- Choose a relationship's `kind` by how it travels. The built-in kinds are `sync`, `async`, `http`, `rpc`, `event`, `queue`, `stream`, `spawn`, `render`, `storage`, and `dependency`. A vault can add its own kinds. Choose the `effect` by what the target does. Use `mutation` for a possible side effect, `query` for a read of held or fetched state, and `compute` for work based only on the inputs. Omit the effect for a `dependency` that only declares a requirement.
- The vault's policy tells [`archboard check code`](../reference/cli/check/#check-code) what evidence each kind accepts. By default, `sync`, `async`, and `render` accept `call` evidence, which includes runtime uses such as a value read or component render. `dependency` accepts `call`, `configured-path`, `import`, and `build-dependency` evidence.
- Draw relationships from source to target, such as from a caller to its callee or a producer to a queue. If one module calls two others in turn, draw both relationships from that module. Record the order of calls and any returns in a sequence flow.

Once the map matches the implementation, ask your agent to adopt the proposal as Current. The following steps build on that state.

## 3. Document three flows

A flow records a single request, background job, or event as an ordered sequence of steps across modules. Pick three paths that matter most to the team:

- A revenue-critical path, such as checkout or a paid API request.
- The highest-traffic request the system handles.
- A background job or failure path that pages on-call engineers.

```text title="Ask your agent" wrap
Add a flow for what happens when a customer pays, from the first request to the receipt.
Anchor each source-backed message to the repository, file, and symbol that shows it.
Read the source again for retries, fixed counts, and calls that a module makes to itself.
```

Render each flow as a sequence diagram:

```bash
archboard model render --flow "Pay for an order" --grammar sequence --out docs/architecture/pay.svg
```

## 4. Create an onboarding walkthrough

A walkthrough steps through a series of readings (beats), each with a title and narrative. For onboarding, start with two modules, add more on each beat until the full path is visible, stop at the main failure point, and finish with the key takeaway.

```text title="Ask your agent" wrap
I am new here. Make an Archboard walkthrough of what happens when a customer pays, in five
or six beats. Start with two modules and add a few at each beat. Stop at the place where it
fails most often, and end on the one thing I must remember.
```

Open the walkthrough in the browser and click **Narrate** to play Codex voice narration for each beat. To export a video, save a checkpoint first, then record from that checkpoint. Pass the `revision.digest` from `archboard model read` to `--expect-revision`, and pass the checkpoint ID returned by `model retain` to `model record`:

```bash
archboard model retain --operation-id keep-pay-walkthrough --writer agent \
  --expect-revision <revision-digest> --doing "keeping the payment walkthrough"
archboard model record --checkpoint <checkpoint-id> --walkthrough "How a customer pays" --out pay.mp4
```

## 5. Decide what fails CI

Run a full check and review every reported finding with the team:

```bash
archboard check
```

Classify each finding code into one of three categories:

- **Fail CI.** Block pull requests whenever this finding appears. [`RELATIONSHIP_UNDRAWN`](../reference/findings/#relationship-undrawn) and [`BINDING_PATH_MISSING`](../reference/findings/#binding-path-missing) are common first choices.
- **Report only.** Show the finding on pull requests without failing the job by adding it to the check Action's [`allow-codes`](../reference/actions/#check-allow-codes) input.
- **Fix the model.** The finding caught a real mismatch in the model. Fix it now.

Save these decisions in the pull request that adds the vault or in your team docs:

```markdown title="Session record"
## Archboard session record

Repository:
Date:
People:

### Findings that fail CI

- CODE: why

### Findings to show without failing

- CODE: why

### Findings that were map mistakes, and the fix

- CODE: what changed

### What the map still gets wrong

-
```

Next, follow [Run checks as a gate](../gate/) to enforce these rules in CI.
