Instructions in `AGENTS.md` are advisory and easy for an agent to skip. `archboard check` is a deterministic CLI gate: given the same model and codebase, it returns the same findings and a standard exit code for hooks, CI, and agent loops.

## What passes and what fails

`archboard check` runs three checks in sequence: semantics, code, and embeds. It exits <Exit outcome="issues" /> if any check reports an error or warning.

| Outcome                    | Exit                                                | Example                                                                                                           |
| -------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Nothing to report          | `0`                                                 | Model matches the codebase                                                                                        |
| Information only           | `0`                                                 | Candidate evidence matched by name only                                                                           |
| Code warning               | <Exit outcome="issues" />                           | [`RELATIONSHIP_UNDRAWN`](../reference/findings/#relationship-undrawn): code calls a module missing from the model |
| Semantic diagnostic        | <Exit outcome="issues" />                           | [`RELATIONSHIP_ON_CONTAINER`](../reference/findings/#relationship-on-container): relationship ends on a container |
| Outdated embed             | <Exit outcome="issues" />                           | [`EMBED_OUTDATED`](../reference/findings/#embed-outdated): tracked SVG or PNG does not match the current model    |
| No vault in checkout       | `0`, or <Exit outcome="issues" /> if an embed warns | Only the embeds check runs, and skipped checks are reported                                                       |
| Usage error or no checkout | <Exit refusal="VAULT_NOT_FOUND" />                  | Run outside a Git checkout with no parent vault                                                                   |
| Server unreachable         | <Exit refusal="SERVER_UNREACHABLE" />               | Local server did not respond and could not start                                                                  |

Information-level findings and skips print to standard error without changing the exit code. See [Check findings](../reference/findings/) for every code. You can also run each check individually:

```bash
archboard check semantics
archboard check code
archboard check embeds
```

## Read a failure

Each code-check warning prints the finding code, the module file in the vault, the affected module, and how to resolve it. Supporting evidence follows on indented lines with its evidence kind, resolution status, file path, and line number:

```text title="stderr"
warning: RELATIONSHIP_UNDRAWN: ZvzEpjXR.module.json: module "Rate card": The code of "Accept parcel" reaches "Rate card". No relationship joins these modules. Add the relationship between the parts that make and answer the call. If this dependency is unintended, change the code.
  configured-path, resolved, services/intake/src/accept.ts:51
  configured-path, resolved, deploy/kubernetes/peer-endpoints.yaml:13
```

Resolve a warning either by updating the model (if the call is intentional) or by changing the code (if it is not). Standard output emits the same findings as JSON for scripts.

<Aside type="caution" title="Do not pipe the check directly">
	Shell pipelines exit with the status of the last command, so `archboard check | tee check.log`
	masks a failing exit code. Redirect the streams instead: `archboard check > check.json 2>
	check.log`.
</Aside>

## Fail on a shallow module

The code check also measures module depth for each bound module. A deep module hides substantial logic behind a small public interface. Exporting a value that external code reads triggers [`EXPOSED_VALUE`](../reference/findings/#exposed-value), a warning on any module.

A module's interface width is the number of symbols callers must learn: exported functions, classes, public methods, and values (exported types do not count). A dispatch function that branches on a closed set of caller-supplied keys, such as `change(vault, "claim" | "release", input)`, counts once per operation. [`MODULE_SHALLOW`](../reference/findings/#module-shallow) fires when every non-type export has a depth finding (such as an exposed value) or when the module averages fewer than 4 units of logic per exported symbol. This threshold is fixed at every size: splitting a module in two or hiding operations behind one key parameter does not reduce the symbols callers must learn.

By default, [`MODULE_SHALLOW`](../reference/findings/#module-shallow) fails the check on every module. If your repository has existing shallow modules, enable debt mode to downgrade existing findings to information and fail only on modules touched by the current branch (including uncommitted changes):

```yaml title=".archboard/vault/.archboard/config.yaml"
codeCheck:
  failShallowModules: true
  rules:
    MODULE_SHALLOW: information
```

With `failShallowModules: true`, every `archboard check` run enforces debt mode locally, in Git hooks, and in CI. To enable it for a single run, pass the flag:

```bash
archboard check --fail-shallow-modules --base main
```

Without `--base`, Archboard uses `origin/HEAD` and falls back to `main`. If the base ref does not resolve, the command exits <Exit refusal="BASE_UNRESOLVED" />.

CI checkouts often lack a local `main` branch or `origin/HEAD`. On pull requests, the [check Action](../reference/actions/) handles this automatically: whenever shallow-module gating can apply (through [`args`](../reference/actions/#check-args), vault configuration, or draft checks), it fetches the pull request's base branch with full history if the checkout is shallow and passes `--base origin/<base branch>`. When the gate is off, it fetches nothing. An explicit `--base` in [`args`](../reference/actions/#check-args) overrides this behavior. On `push` workflows, pass `--base` explicitly and set `fetch-depth: 0` on `actions/checkout`:

```yaml
- uses: miklschmidt/archboard/actions/check@{{sha}} # {{ref}}
  with:
    version: "{{version}}"
    args: --base origin/main
```

## Set the level of a module-depth rule

The code check reports seven module-depth codes: [`EXPOSED_VALUE`](../reference/findings/#exposed-value), [`EXPOSED_VALUE_COMPUTED`](../reference/findings/#exposed-value-computed), [`CODE_PASS_THROUGH`](../reference/findings/#code-pass-through), [`REEXPORT_PASS_THROUGH`](../reference/findings/#reexport-pass-through), [`EXPOSED_UNUSED`](../reference/findings/#exposed-unused), [`INTERFACE_UNDECLARED`](../reference/findings/#interface-undeclared), and [`MODULE_SHALLOW`](../reference/findings/#module-shallow). Several default to warning severity and fail the check immediately after an upgrade unless configured otherwise.

To downgrade or disable a rule across the repository, configure `codeCheck.rules` in the vault configuration:

```yaml title=".archboard/vault/.archboard/config.yaml"
codeCheck:
  rules:
    EXPOSED_VALUE: information
    CODE_PASS_THROUGH: "off"
```

Setting a rule to information keeps its findings in the output (noting the vault policy override) without failing the check. Setting a rule to `"off"` omits those findings from CLI output, Measures, and PR annotations, and prints a summary line such as `code check: off by vault policy: CODE_PASS_THROUGH`. Any unconfigured code keeps its built-in severity.

Rules can only lower severity, not raise it. Shallow-module detection runs before rules are applied, so turning off exposed-value rules does not change which modules count as shallow. Unknown codes or unsupported levels (such as `warning`) fail the semantics check, as does disabling [`MODULE_SHALLOW`](../reference/findings/#module-shallow) while `failShallowModules: true` is set. Remove any entry for the retired width-cap rule to keep the configuration valid. Passing `--fail-shallow-modules` while [`MODULE_SHALLOW`](../reference/findings/#module-shallow) is set to `"off"` exits with <Exit refusal="SHALLOW_RULE_CONFLICT" />.

## In a Git hook

A `pre-push` hook prevents pushing changes when the architecture check fails. Save this script as `.githooks/pre-push` and make it executable:

```sh title=".githooks/pre-push" frame="code"
#!/bin/sh
# Block the push while the architecture check fails.
# Skip it once with: git push --no-verify
archboard check > /dev/null
```

Point Git at `.githooks` once per clone:

```bash
chmod +x .githooks/pre-push
git config core.hooksPath .githooks
```

In a Node.js repository, pin `archboard` in `devDependencies` so `npm install` configures the hook path automatically:

```json title="package.json" ins={3,6}
{
	"scripts": {
		"prepare": "test -e .git && git config core.hooksPath .githooks || true"
	},
	"devDependencies": {
		"archboard": "{{version}}"
	}
}
```

Replace `archboard check` in `.githooks/pre-push` with `./node_modules/.bin/archboard check` so local pushes run the exact version pinned for CI. A `pre-commit` hook works the same way, though running full checks on push avoids slowing down every commit in large repositories.

## In CI

The check Action installs the CLI, runs `archboard check`, annotates findings on the pull request diff, and fails the job on any warning or semantic diagnostic:

```yaml title=".github/workflows/architecture.yml" ins={19,21,24}
name: architecture
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 22
      # The checkout's own TypeScript is the default TypeScript server.
      - run: npm ci
      # A server for each other language in .archboard/language-servers.json.
      - run: pip install pyright
      - uses: miklschmidt/archboard/actions/check@{{sha}} # {{ref}}
        with:
          version: "{{version}}"
```

Install dependencies and language servers before running the check Action. The code check requires a language server to resolve symbols, and only resolved evidence produces warnings. `npm ci` installs the repository's TypeScript version (built-in support starts at TypeScript {reference.facts.nativeTypescript}, and earlier versions also require `typescript-language-server` in `devDependencies`). Install servers for any other languages configured in `.archboard/language-servers.json`, such as `pip install pyright` for Python. Without a language server, unresolved references remain information-level and do not fail the check.

Pin [`version`](../reference/actions/#check-version) to the CLI release your team runs. Without it, the Action installs the CLI matching its own release. Pin the Action itself to a commit SHA (with the tag `{{ref}}` in a comment) because Git tags can move. See the [GitHub Actions reference](../reference/actions/) for all inputs, including [`fail-on: never`](../reference/actions/#check-fail-on) (report findings without failing, except when a vault is missing) and [`allow-codes`](../reference/actions/#check-allow-codes) (report specific codes without failing).

Other CI systems can run `archboard check` directly and gate on its exit code:

```yaml title=".gitlab-ci.yml"
architecture:
  image: node:22
  script:
    - npm ci
    - npm install --global archboard@{{version}}
    - archboard check > check.json
  artifacts:
    when: always
    paths: [check.json]
```

<Aside type="note" title="Bindings to other repositories">
	Bindings pointing to an unregistered repository are skipped as
	[`repository-unregistered`](../reference/findings/#repository-unregistered), and skips do not fail
	the check. Check out and register every repository your bindings reference. See [Application and
	infrastructure](../platform/) for multi-repo CI setup.
</Aside>

## In an agent loop

Pass check failures back to your coding agent so it fixes the code or model while it still has context. Three setups work well:

### Claude Code Stop hook

A `Stop` hook runs when Claude Code finishes a turn. When the hook ends with status `2`, Claude Code passes standard error back to the agent and continues working:

```json title=".claude/settings.json"
{
	"hooks": {
		"Stop": [
			{
				"hooks": [
					{
						"type": "command",
						"command": "archboard check > /dev/null 2> /tmp/archboard-check.log || { cat /tmp/archboard-check.log >&2; exit 2; }"
					}
				]
			}
		]
	}
}
```

### Shell loop for any agent

Run the agent, run `archboard check`, and feed any findings back until the check passes or the retry limit is reached:

```bash title="agent-loop.sh" frame="code"
#!/usr/bin/env bash
# Ask the agent for a change, then hold it to the architecture check.
set -u
task="$1"
codex exec "$task"
for round in 0 1 2 3; do
  if archboard check > /dev/null 2> check.log; then
    echo "archboard check passed after round $round"
    exit 0
  fi
  if [ "$round" -eq 3 ]; then
    break
  fi
  codex exec "archboard check failed. Fix the code or the Archboard model so that it passes. Do not hide a finding. The findings:
$(cat check.log)"
done
echo "archboard check still fails after 3 rounds" >&2
exit 1
```

### Repository instructions

Add a rule to `AGENTS.md` so agents run the check before finishing:

```markdown title="AGENTS.md"
Run `archboard check` before you finish. It fails while the architecture model and the code
disagree. Fix the code or the model. Never silence a finding.
```

Instructions alone are advisory, so pair them with a hook, shell loop, or CI gate.

## Keep embedded diagrams current

Diagrams committed for READMEs and ADRs are embeds: Git-tracked SVG or PNG files generated by Archboard. The embeds check fails when an embed falls behind the model. Regenerate outdated embeds and commit them:

```bash
archboard check embeds --fix
git add docs/architecture
```
