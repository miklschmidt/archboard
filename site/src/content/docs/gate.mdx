A rule in `AGENTS.md` is a request. An agent can ignore it. A check that fails the build is a fact that the agent must deal with. `archboard check` is deterministic: the same model and the same code give the same answer, with an exit code that CI understands.

## What passes and what fails

`archboard check` runs three checks in order: semantics, code, then embeds. It exits <Exit outcome="issues" /> while one of them has something that you must fix.

| Outcome                       | Exit                                                  | Example                                                                                                                  |
| ----------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Nothing to report             | `0`                                                   | A model that matches its code                                                                                            |
| Information only              | `0`                                                   | A relationship whose evidence is a candidate, matched by name only                                                       |
| A code warning                | <Exit outcome="issues" />                             | [`RELATIONSHIP_UNDRAWN`](../reference/findings/#relationship-undrawn): code calls a module that the model does not join  |
| A semantic diagnostic         | <Exit outcome="issues" />                             | [`RELATIONSHIP_ON_CONTAINER`](../reference/findings/#relationship-on-container): a line that ends on a module with parts |
| An outdated picture           | <Exit outcome="issues" />                             | [`EMBED_OUTDATED`](../reference/findings/#embed-outdated): a tracked SVG that no longer matches the model                |
| No vault in the checkout      | `0`, or <Exit outcome="issues" /> when an embed warns | Only the embeds check runs, and a skip says that the others did not                                                      |
| A usage error, or no checkout | <Exit refusal="VAULT_NOT_FOUND" />                    | Outside any Git checkout, with no vault above it                                                                         |
| No server                     | <Exit refusal="SERVER_UNREACHABLE" />                 | The server did not answer and could not start                                                                            |

Information and skips print on standard error and never change the exit status. [Check findings](../reference/findings/) lists every code. Each check also runs alone:

```bash
archboard check semantics
archboard check code
archboard check embeds
```

## Read a failure

A warning of the code check names its code, the file of the module in the vault, the module and what to do. Each piece of evidence follows on its own line, with its kind, whether it is resolved, and its file and line:

```text title="stderr"
warning: RELATIONSHIP_UNDRAWN: ZvzEpjXR.module.json: module "Rate card": The code of "Accept parcel" reaches "Rate card". No relationship joins these modules. Add the relationship between the parts that make and answer the call. If this dependency is unintended, change the code.
  configured-path, resolved, services/intake/src/accept.ts:51
  configured-path, resolved, deploy/kubernetes/peer-endpoints.yaml:13
```

There are two fixes, and the finding says both. If the call is intended, the agent draws the relationship. If it is not, the agent changes the code. Either way the next check passes. The JSON answer on standard output carries the same findings for a script.

<Aside type="caution" title="Do not pipe the check">
	A pipeline exits with the status of its last command, so `archboard check | tee check.log` hides a failing check. Redirect the streams instead: `archboard check > check.json 2> check.log`.
</Aside>

## Fail on a shallow module

The code check also judges how deep each bound module is. A deep module hides much logic behind few names. An exported value that code outside the module reads is [`EXPOSED_VALUE`](../reference/findings/#exposed-value), a warning on any module.

Two warnings judge each module as a whole. Its width is the number of names that callers must learn: its exported functions, classes, public methods and values. Exported types do not count. [`INTERFACE_WIDE`](../reference/findings/#interface-wide) names a module whose width is above 20. [`MODULE_SHALLOW`](../reference/findings/#module-shallow) names a module whose every export that is not a type has a finding like an exposed value, or a module with a width of at least 8 and fewer than 4 pieces of logic behind each name. The thresholds are fixed.

Both codes fail the check on every module. If your repository is not ready for that, use debt mode. Set both codes to information, and fail only on the modules that a branch touched, uncommitted changes included:

```yaml title=".archboard/vault/.archboard/config.yaml"
codeCheck:
  failShallowModules: true
  rules:
    INTERFACE_WIDE: information
    MODULE_SHALLOW: information
```

With `failShallowModules: true`, every plain `archboard check` runs the gate, in a hook and in CI too. The flag runs it for one command:

```bash
archboard check --fail-shallow-modules --base main
```

Without `--base`, the default base decides: where `origin/HEAD` points, else `main`. A base that does not resolve exits <Exit refusal="BASE_UNRESOLVED" />, never `0`.

A CI checkout may have no `main` branch and no `origin/HEAD`. On a pull request, the [check Action](../reference/actions/) needs neither: when the gate can be on, by the flag in its [`args`](../reference/actions/#check-args), by the configuration, or because the args check drafts, which keep the setting each was made with, it fetches the pull request's base branch, with the whole history when the checkout is shallow, and passes it as `--base origin/<base branch>`. With the gate off, it fetches nothing. A `--base` in the args wins. On a push, name the base there, and give `actions/checkout` the history with `fetch-depth: 0`:

```yaml
- uses: miklschmidt/archboard/actions/check@{{sha}} # {{ref}}
  with:
    version: "{{version}}"
    args: --base origin/main
```

## Set the level of a module-depth rule

The code check reports eight module-depth codes: [`EXPOSED_VALUE`](../reference/findings/#exposed-value), [`EXPOSED_VALUE_COMPUTED`](../reference/findings/#exposed-value-computed), [`CODE_PASS_THROUGH`](../reference/findings/#code-pass-through), [`REEXPORT_PASS_THROUGH`](../reference/findings/#reexport-pass-through), [`EXPOSED_UNUSED`](../reference/findings/#exposed-unused), [`INTERFACE_UNDECLARED`](../reference/findings/#interface-undeclared), [`INTERFACE_WIDE`](../reference/findings/#interface-wide) and [`MODULE_SHALLOW`](../reference/findings/#module-shallow). Several are warnings, so they fail the check. If you upgrade and write no rules, your repository gets these warnings, and the check fails on them.

To lower a code for the whole repository, set its level in the vault's configuration:

```yaml title=".archboard/vault/.archboard/config.yaml"
codeCheck:
  rules:
    EXPOSED_VALUE: information
    CODE_PASS_THROUGH: "off"
```

A code set to information stays in the answer, and its warnings become information, which never fails the check. Its message says that the vault policy set it. A code set to off has no findings at all: no line, no count, nothing in Measures and no annotation. The check prints one line that names the codes that are off, for example `code check: off by vault policy: CODE_PASS_THROUGH`. A code without a rule keeps its built-in level.

A rule can only lower a code. The check derives shallow modules before it applies the rules, so a rule that turns off exposed values does not change which modules are shallow. Another code, or another level such as warning, makes the configuration invalid, and the semantics check names the entry. A rule that turns off the shallow-module code or the wide-interface code beside `failShallowModules: true` is invalid too, because the gate fails on them. Beside `--fail-shallow-modules`, the check refuses with <Exit refusal="SHALLOW_RULE_CONFLICT" />.

## In a Git hook

A `pre-push` hook keeps a failing map off the remote. Save this as `.githooks/pre-push` and make it executable:

```sh title=".githooks/pre-push" frame="code"
#!/bin/sh
# Block the push while the architecture check fails.
# Skip it once with: git push --no-verify
archboard check > /dev/null
```

Point Git at the directory once per clone:

```bash
chmod +x .githooks/pre-push
git config core.hooksPath .githooks
```

In a Node.js repository, pin the CLI as a dev dependency and let `npm install` set the hook path for every clone:

```json title="package.json" ins={3,6}
{
	"scripts": {
		"prepare": "test -e .git && git config core.hooksPath .githooks || true"
	},
	"devDependencies": {
		"archboard": "{{version}}"
	}
}
```

For this setup, replace `archboard check` in `.githooks/pre-push` with `./node_modules/.bin/archboard check`. The hook then runs the pinned program, the same one that CI runs. A `pre-commit` hook works the same way, but a full check on every commit is slow on a large repository. Push is the better moment.

## In CI

The check Action installs the CLI, runs `archboard check`, and turns each finding into an annotation on the pull request's diff. It fails the job on a warning or a diagnostic:

```yaml title=".github/workflows/architecture.yml" ins={19,21,24}
name: architecture
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 22
      # The checkout's own TypeScript is the default TypeScript server.
      - run: npm ci
      # A server for each other language in .archboard/language-servers.json.
      - run: pip install pyright
      - uses: miklschmidt/archboard/actions/check@{{sha}} # {{ref}}
        with:
          version: "{{version}}"
```

The code check resolves a name only through a language server, and only resolved evidence makes a warning. So install the dependencies first. `npm ci` installs the checkout's own TypeScript, which serves from version {reference.facts.nativeTypescript}. Before {reference.facts.nativeTypescript}, the check also needs `typescript-language-server` in the dev dependencies. Install the server of each other language that `.archboard/language-servers.json` names, as `pip install pyright` does for Python. Without a server, a call that needs resolved evidence stays information, and the gate passes.

Pin [`version`](../reference/actions/#check-version) to the release that your team runs, as you pin your compiler. Without it, the Action installs the CLI of the release that it comes from. The examples pin the Action to the commit of `{{ref}}`, with the tag in a comment. A tag can move, and a commit cannot, so pin any third-party Action this way. The [Actions reference](../reference/actions/) lists every input: [`fail-on: never`](../reference/actions/#check-fail-on) reports findings without failing, though a checkout without a vault still fails, and [`allow-codes`](../reference/actions/#check-allow-codes) keeps chosen findings visible without failing on them.

Any other CI runs the same command. The exit code is the gate:

```yaml title=".gitlab-ci.yml"
architecture:
  image: node:22
  script:
    - npm ci
    - npm install --global archboard@{{version}}
    - archboard check > check.json
  artifacts:
    when: always
    paths: [check.json]
```

<Aside type="note" title="Bindings into other repositories">
	A binding into a repository that the CI machine has not registered is skipped as
	[`repository-unregistered`](../reference/findings/#repository-unregistered), and a skip never
	fails the check. Check out each repository that your bindings name, and register it. [Application
	and infrastructure](../platform/) shows how.
</Aside>

## In an agent's loop

Give the check's words back to the agent before a person reviews the work. The agent then fixes the map or the code while it still holds the context. Three ways work today.

### Claude Code: a hook when it stops

A `Stop` hook runs when Claude Code wants to finish. When the hook ends with status `2`, Claude Code gives the hook's standard error back to Claude, and Claude goes on working:

```json title=".claude/settings.json"
{
	"hooks": {
		"Stop": [
			{
				"hooks": [
					{
						"type": "command",
						"command": "archboard check > /dev/null 2> /tmp/archboard-check.log || { cat /tmp/archboard-check.log >&2; exit 2; }"
					}
				]
			}
		]
	}
}
```

### Any agent: a loop in the shell

Run the agent, run the check, and give the findings back until the check passes or the rounds run out:

```bash title="agent-loop.sh" frame="code"
#!/usr/bin/env bash
# Ask the agent for a change, then hold it to the architecture check.
set -u
task="$1"
codex exec "$task"
for round in 0 1 2 3; do
  if archboard check > /dev/null 2> check.log; then
    echo "archboard check passed after round $round"
    exit 0
  fi
  if [ "$round" -eq 3 ]; then
    break
  fi
  codex exec "archboard check failed. Fix the code or the Archboard model so that it passes. Do not hide a finding. The findings:
$(cat check.log)"
done
echo "archboard check still fails after 3 rounds" >&2
exit 1
```

### In the instructions of the repository

Tell the agent where the gate is, so it runs the check before it says it is done:

```markdown title="AGENTS.md"
Run `archboard check` before you finish. It fails while the architecture model and the code
disagree. Fix the code or the model. Never silence a finding.
```

An instruction alone is a request, so keep the hook or the loop as the gate.

## Keep the pictures current

Pictures in your README and ADRs are embeds: SVG or PNG files that Archboard drew and Git tracks. The embeds check fails when one no longer matches the model. Draw them again and commit them:

```bash
archboard check embeds --fix
git add docs/architecture
```
